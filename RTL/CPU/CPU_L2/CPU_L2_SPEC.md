## 1. 目的と効果の見込み

実機の PMU で Linux の負荷を数えると(`BENCH.md` 14 章)、**カーネルが主の負荷はサイクルの
5〜7 割を L1 のミス待ちに使っている**。I$ ミスは 1000 命令あたり 19〜61、D$ ミスは 15〜31
(CoreMark はそれぞれ 0.49、0.16)。カーネルのコードとデータは 16 KB の L1 に収まらない。

L1 のミス 1 回の重さは、理想的なメモリで 12〜13 サイクル(`CPU_CACHE_SPEC.md` 8.4、64 B を
8 ビートで受ける)、実機で 30〜50 サイクル(PMU から逆算)。差の **20〜35 サイクルが LiteDRAM
までの往復**で、L2 がヒットすればそこが 2〜3 サイクルになる。

見込み(L1 のミスの 6〜8 割が L2 にヒットし、1 回 約 20 サイクル縮むとして。
`BENCH.md` 14 章の数字から):

| 負荷 | L1 ミス / 1000 命令 | CPI | 減るサイクル | 速くなる |
|---|---|---|---|---|
| `tftp` | 93 | 4.80 | 約 27 % | 約 1.37 倍 |
| `ext4read` / `sdread` | 65〜70 | 4.0〜4.5 | 約 22 % | 約 1.28 倍 |
| `ls -lR` | 47 | 3.08 | 約 21 % | 約 1.27 倍 |
| `forkexec` | 37 | 2.74 | 約 19 % | 約 1.23 倍 |
| `gunzip` / `awk` | 4〜5 | 1.4〜1.7 | 約 4 % | |
| `md5sum`(流れる読み出し) | 4 | 1.22 | 1〜2 % | (先読みなら効く。8 章) |
| CoreMark | 0.6 | 1.13 | ほぼ 0 | |

ヒット率は実装して測るまで分からない。L2 用の性能カウンタのイベントを足して実機で数える(7 章)。

## 2. 置き場所とつなぎ方

```
  CPU_TOP
  ┌───────────────────────────────────────────────────────────────┐
  │ CPU_CORE ─ i_* / d_* ─ CPU_CACHE(I$ / D$ ─ BUS_ARB)          │
  │                               │ AXI4 64 bit(メモリバス)       │
  │                               ▼                               │
  │                        CPU_L2(新設) ────────────────────────────┼─ m_axi4 → LiteX
  │                                                               │   AXIUpConverter(64→128)
  │ CPU_DBG ─ DBG_CACHE ─▶ D$ の第 2 ポート                        │   → LiteDRAMAXI2Native
  │ DMA ポート ───────────▶ D$ の第 2 ポート                        │   → LiteDRAM(DDR3 16 bit)
  │                        AXI4-Lite(周辺、キャッシュしない)──────────┼─ m_axil(L2 を通らない)
  └───────────────────────────────────────────────────────────────┘
```

- **`CPU_CACHE` のメモリバス(AXI4、64 ビット)と `CPU_TOP` の `m_axi4` の間**に、AXI4 の
  スレーブとマスタを 1 つずつ持つブロックとして挟む。コア・L1・`BUS_ARB`・LiteX の側は何も
  変えない(`core.py` も LiteX のチェックアウトも変更なし)。
- **主記憶へ行くものはすべてここを通る**: I$ / D$ の fill、D$ の書き戻し、SD カードの DMA
  (D$ の第 2 ポート経由)、デバッガのメモリアクセス(同)。ほかに主記憶を触る経路は無い
  (Ethernet のバッファは SoC の SRAM)。したがって **L2 は作りからして一貫している**。
  後始末(フラッシュの命令、無効化)は要らない。
- LiteX 自身の L2(`--l2-size`)は SoC バスの側にあり、CPU のメモリバスはそれを通らない。
  使えない(`build_soc.sh` の注記、`BRINGUP.md`)。
- `CPU_TOP` のパラメータ `L2_SIZE`(0 なら L2 なしでそのままつなぐ)。L2 の有無を比べる
  ビルド、デバッグ論理の単体ビルド(`FPGA/ARTY_A7_100T`)のため。

## 3. 方式(案)

| 項目 | 案 | 理由・代案 |
|---|---|---|
| 容量 | **256 KB**(パラメータ。128 KB にもできる) | ブロック RAM が 94 タイル余っている(5 章)。カーネルの頻繁に使うコードとデータは数百 KB と見て大きめ。タイミングや配置が苦しければ 128 KB |
| 連想度 | **4 ウェイ** | L1(4 ウェイ、1 ウェイ 4 KB の VIPT)の索引の偏りを受け止める。8 ウェイはタグ比較とウェイ選択が倍、ダイレクトマップは衝突が多い |
| 行 | **64 B**(L1 と同じ) | L1 の fill 1 回 = L2 の 1 行。行を分けたり継いだりしない |
| 置き換え | **疑似 LRU**(1 セット 3 ビット、LUT RAM) | 代案は L1 と同じ乱数(パラメータ)。乱数でも大差なければそちら |
| 包含関係 | **非包含**(L1 にあるものが L2 にあるとは限らない) | 包含にすると L2 の追い出しで L1 を無効化する経路が要る。一貫性は 2 章の理由で不要 |
| 書き方 | **書き戻し**。行全体の書き込み(D$ の書き戻し)は読まずに確保(ヒットでもミスでも L2 に書いてダーティ)。**一部だけの書き込み**(デバッガのライトスルー `STWTHR`)は**ライトスルー・非割り当て**: メモリへ必ず書き、L2 にあればその語も更新する(ダーティにはしない) | 一部だけの書き込みはデバッガだけ。ライトスルーにしておけば、デバッガが書いたメモリは L2 を消しても残る(`SIM_OCD` の「RAM kept over ndmreset」、`CPU_CACHE_SPEC.md` 4.7 と同じ考え) |
| 同時に扱う要求 | **1 本ずつ**(到着順)。追い出す行の書き戻しは **1 行の追い出しバッファ**に入れて、fill を先に済ませる | L1 の MSHR 2 本・書き戻しバッファ 2 本の重なりは L2 で直列になるが、コアは順番どおりに 1 命令ずつなので失うものは小さい。ミス中のヒット(hit-under-miss)は 8 章の拡張 |
| メモリ側 | AXI4 64 ビット、8 ビートのバースト(今と同じ) | LiteX 側を変えない。128 ビット(LiteDRAM の幅)は 8 章の拡張 |
| リセット | CPU のリセット(システムリセット、`ndmreset`)で**中身を捨てる**。リセット後、約 1,000 サイクルかけてタグの有効ビットを消し、その間は要求を待たせる | L1 と同じ扱い。ダーティ行はリセットで失われるが、それは L1 の今と同じ。デバッガの書き込みはライトスルーなので残る(上)。代案は 9 章 |

## 4. 動作

L2 が受ける要求は 3 種類だけ(`CPU_CACHE` の作り。AMO や LR / SC は D$ の中で済む)。

| 要求 | 出す側 | ヒット | ミス |
|---|---|---|---|
| 行の読み出し(AR、8 ビート) | I$ / D$ の fill | L2 から 8 ビートを返す | 置き換える行を選ぶ。ダーティなら追い出しバッファへ。メモリから 8 ビート読んで、**届いた順に L1 へも返しながら**(fill の待ちを延ばさない)L2 に書く。追い出しバッファはその後メモリへ書く |
| 行の書き込み(AW、8 ビート、全バイト有効) | D$ の書き戻し | その行に上書き、ダーティ | 置き換える行を選び(ダーティなら追い出し)、読まずに書く、ダーティ |
| 一部の書き込み(AW、1 ビート、ストローブ) | デバッガのライトスルー | メモリへ書く。L2 のその語もストローブで更新(ダーティのまま / きれいのまま変えない) | メモリへ書くだけ(確保しない) |
| 一部の読み出し(AR、1 ビート) | (今は無い。来たら行の読み出しの 1 ビート目だけ返す) | | |

**順序**。1 本ずつ到着順に処理するので、同じ行への書き戻しと読み出しの追い越しは起きない。
追い出しバッファにある行への読み出しは、バッファから答える(メモリへの書き込みを待たない)。

**ヒットの流れ**(行の読み出し、64 ビット × 8):

| サイクル | |
|---|---|
| t | AR を受ける。索引でタグとデータのブロック RAM を読む(4 ウェイ同時) |
| t+1 | タグ比較 → ヒットしたウェイを選ぶ(1 段レジスタ) |
| t+2 | 1 ビート目(R)。以後 1 サイクル 1 ビート、t+9 で 8 ビート目(RLAST) |

L1 から見ると、今のミス(理想的なメモリで 12〜13 サイクル)に 2 サイクル足した 14〜15
サイクル。実機の 30〜50 サイクルより 15〜35 サイクル短い。

**ミスの流れ**。メモリへの AR を出し、返ってくるビートを L1 へ流しながらデータ RAM に
書き、最後にタグを書く。L1 から見た遅延は今とほぼ同じ(+1〜2 サイクル)。

## 5. 資源とタイミングの見積もり

| 資源 | 256 KB | 128 KB | 今(`BENCH.md` 13 章の版) | 合計(256 KB) |
|---|---|---|---|---|
| ブロック RAM | データ 64 タイル(4 ウェイ × 64 KB、RAMB36 は 4 KB)+ タグ 2 タイル | 32 + 2 | 40.5 | 約 107 / 135(79 %) |
| LUT | 2,500〜4,000(制御、タグ比較 4 本、ウェイ選択 64 ビット × 4、AXI の両側、追い出しバッファ) | 同じ | 45,598 | 48,000〜50,000(76〜79 %) |
| FF | 1,500〜2,500(追い出しバッファ 512 ビットを含む) | 同じ | 27,006 | 約 23 % |
| DSP | 0 | 0 | 32 | |

- **タイミング**: L2 はメモリバスの上にだけあり、コアの最悪経路(EX の分岐比較 → IFU、
  `TIMING.md` 31 章)とは交わらない。ブロック RAM の読み出しはレジスタで受ける。気を付けるのは、
  66 タイルのブロック RAM がダイの複数の列に散らばり、L2 の制御からの配線が長くなること。
  データのウェイ選択の後に 1 段のレジスタを置く(上の t+2)。
- **スライス**: いま 88.6 %(`ROADMAP.md`)。+2,500〜4,000 LUT で 92〜94 % 程度になる見込み。
  これが C2(FPU のパイプライン化)に残る余地を決めるので、L2 を入れた版で実測してから
  C2 の予算を決める(10 章)。

## 6. 一貫性・リセット・デバッグとの関係

- **DMA、デバッガ、fence.i**: すべて D$ を通るので、L2 から見ると普通の fill と書き戻し
  (`fence.i` は D$ のダーティ行を書き戻し、I$ はその後 L2 から fill する。L2 は I$ と D$ で
  共通なので新しい内容が見える)。
- **キャッシュしない領域**(`MEM_BASE` 未満、AXI4-Lite)は L2 を通らない。
- **`ndmreset` / `hartreset`(デバッガの CPU リセット)**: 3 章のとおり中身を捨てる。OpenOCD の
  `reset halt` の後、BIOS は空の L2 から始まる(1,000 サイクルの消去は BIOS の最初の命令の前に
  終わる)。
- **電源投入**: 同じく消去してから要求を受ける。

## 7. 性能カウンタ

`CPU_CORE_SPEC.md` 決定 69 のイベントに 2 つ足す(`HPM_EVENTS` 18 → 20)。L2 から `CPU_TOP`
経由でコアへ(L1 の `ev_ic_refill` / `ev_dc_refill` と同じ形)。

| 番号 | イベント | perf |
|---|---|---|
| 18 | L2 への行の読み出し(L1 の fill) | `LLC-loads`(デバイスツリーの `pmu` ノードでキャッシュイベント 0x10010 に対応させる)、`r12` |
| 19 | そのうち L2 のミス | `LLC-load-misses`(0x10011)、`r13` |

`workload.sh` に L2 のヒット率の列を足す。

## 9. 未決事項

1. **容量**: 256 KB で始め、配置・タイミングが苦しければ 128 KB。ブロック RAM の余裕だけなら
   256 KB は入る。
2. **置き換え**: 疑似 LRU と乱数を、実機の `workload.sh` で比べて決める(パラメータで両方持つ)。
3. **CPU のリセットで中身を捨てるか**: 案は捨てる(L1 と同じ)。残す案は、L2 の配列を
   `ndmreset` の外に置き、AXI のやり取りだけをリセットする。ダーティ行が失われないが、
   リセットの途中で止まった AXI のやり取りの後始末が要る。今のところ利点が小さい。
4. **追い出しバッファを 1 行で足りるか**: D$ の書き戻しと fill が続けて来る形(`CPU_CACHE_SPEC.md`
   8.4 の「ダーティ追い出し」)で詰まらないかをシミュレーションで見る。
