# mmRISC-2 L1 キャッシュ 仕様書

- 版: Rev-2 (2026-09-19) 実装にあわせて改訂(Rev-1 の設計計画と実装仕様を統合)
- 対象: `RTL/CPU/CPU_CACHE/`(L1 命令/データキャッシュ)、`SIM/SIM_CACHE`(検証)、
  `RTL/CPU/CPU_TOP/`(組み込み)
- 既定値は LiteX + Rocket `LitexConfig_linux_1_1` の L1 と同等。
  セット数・ウェイ数・ブロックサイズ・命令/データ別をパラメータ化する。
- 関連: `RTL/CPU/CPU_DBG/CPU_DBG_SPEC.md`(デバッグ論理)

Rev-1(設計計画)からの主な変更は 9 章にまとめてある。

---

## 1. 目的と範囲

CPU コア(パイプライン)と MMU は次フェーズで実装する。本フェーズでは
**L1 命令キャッシュと L1 データキャッシュ**を作り、メモリバス(AXI4)・
周辺バス(AXI4-Lite)へ接続して、テストベンチの CPU BFM で検証する。

| 項目 | 本フェーズ |
|---|---|
| L1 命令キャッシュ (I$) | **実装済み** |
| L1 データキャッシュ (D$) | **実装済み** |
| 非キャッシュアクセス経路 | **実装済み**(`MEM_BASE` 未満は周辺バスへ素通し) |
| AMO / LR-SC (A 拡張) | **実装済み**(D$ 内で処理) |
| `FENCE` / `FLUSH` / `fence.i` | **実装済み**(キャッシュ全体に対する操作) |
| ライン単位のフラッシュ・無効化 | 未実装(必要になった時点で追加) |
| MMU (Sv39) / TLB | 次フェーズ。本フェーズは物理アドレスを直接受け取る |
| デバッグアクセスのキャッシュ経由化 | **実装済み**(4.7)。メモリバス側はデバッガも D$ を通る |
| L2 キャッシュ | 実装しない(CPU ブロック完成後に検討。Arty A7-100T の BRAM 量では 512KiB は載らない) |
| Zicbom などのキャッシュ管理命令 | 実装しない(将来) |
| ECC / パリティ | 実装しない |

## 2. 位置づけとブロック構成

### 2.1 現在(CPU コア未実装)

```
            CPU コア(未実装、いまは SIM_CACHE の CPU BFM)
              │ 命令フェッチ            │ ロード/ストア/AMO
              ▼                         ▼
        ┌───────────┐            ┌───────────┐
        │  ICACHE   │            │  DCACHE   │
        └─────┬─────┘            └─────┬─────┘
              │ AXI4 (fill)            │ AXI4 (fill / writeback)
              └──────────┬─────────────┘
                    BUS_ARB(2 マスタ)
                         │ メモリバス AXI4        周辺バス AXI4-Lite
                         ▼                        ▼(非キャッシュ)
                    CPU_TOP のポート
```

### 2.2 CPU コアと MMU を実装したあとの姿

```
                          CPU_TOP
  ┌────────────────────────────────────────────────────────────────────────┐
  │  CPU コア                                                               │
  │   命令フェッチ ──┐                     ┌── ロード/ストア、AMO          │
  │                  ▼                     ▼                               │
  │            ┌──────────┐          ┌──────────┐                          │
  │            │ ITLB     │          │ DTLB     │  ← MMU(次フェーズ)        │
  │            └────┬─────┘          └────┬─────┘                          │
  │                 │ 物理アドレス        │ 物理アドレス                    │
  │            ┌────▼─────┐          ┌────▼─────┐                          │
  │            │  ICACHE  │          │  DCACHE  │ ← デバッグアクセスもここ  │
  │            └────┬─────┘          └────┬─────┘   を通る(4.7)            │
  │                 │ fill                │ fill / 書き戻し / 非キャッシュ  │
  │            ┌────▼─────────────────────▼─────┐                          │
  │            │ BUS_ARB                        │                          │
  │            └────┬──────────────────────┬────┘                          │
  └─────────────────┼──────────────────────┼───────────────────────────────┘
             メモリバス AXI4           周辺バス AXI4-Lite
```

- キャッシュは**物理アドレス**で索引・比較する(PIPT)。MMU 実装後は TLB が出す
  物理アドレスをそのまま渡せばよく、キャッシュ側の変更は不要。
- アドレスのビット幅は CPU 側の設定に合わせる(`PADDR_WIDTH`、既定 40)。
  タグ幅はここから index / offset を引いた残りになる。

### 2.3 モジュール一覧

| モジュール | 置き場所 | 内容 |
|---|---|---|
| `CPU_CACHE` | `RTL/CPU/CPU_CACHE/CPU_CACHE/` | I$ + D$ + `BUS_ARB`。AXI4 を 1 本にまとめる |
| `ICACHE` | `RTL/CPU/CPU_CACHE/ICACHE/` | 命令キャッシュ |
| `DCACHE` | `RTL/CPU/CPU_CACHE/DCACHE/` | データキャッシュ(MSHR、書き戻し、AMO/LR-SC) |
| `CACHE_TAG_ARRAY` | `RTL/CPU/CPU_CACHE/CACHE_TAG_ARRAY/` | タグ + 有効 + ダーティ。ウェイ数分を並列に読む |
| `CACHE_DATA_ARRAY` | `RTL/CPU/CPU_CACHE/CACHE_DATA_ARRAY/` | データ。64bit 単位、バイトイネーブル付き |
| `CACHE_PORT_ARB` | `RTL/CPU/CPU_CACHE/CACHE_PORT_ARB/` | D$ の CPU ポートを CPU(優先)とデバッグで共有する |

配列は FPGA の Block RAM 推論を前提とする(同期読み出し、1 サイクル遅れ)。
タグ配列とデータ配列は `initial` で 0 に初期化する(FPGA の Block RAM と同じ)。

`ICACHE` / `DCACHE` の組み合わせ回路は `always_comb` ではなく `always @(*)`
で書く。Icarus Verilog は、可変インデックスで参照している変数への代入ごとに
`always_comb` を再起動するため、組み合わせ網が同一時刻で無限ループする。
`always @(*)` は値が変化したときだけ再評価され、合成結果は同じである。

## 3. パラメータ

### 3.1 共通

| パラメータ | 既定 | 内容 |
|---|---|---|
| `PADDR_WIDTH` | 40 | CPU から受け取る物理アドレス幅。CPU_TOP の `AXI4_ADDR_WIDTH` と合わせる |
| `XLEN` | 64 | データ幅。AXI4 のデータ幅と同じ |
| `MEM_BASE` | `0x00_8000_0000` | これ以上がキャッシュ対象(メモリバス)。未満は非キャッシュ(周辺バス) |
| `AXI4_ID_WIDTH` | 4 | メモリバスの ID 幅 |

### 3.2 ICACHE

| パラメータ | 既定 | 内容 |
|---|---|---|
| `SETS` | 64 | セット数(2 のべき乗) |
| `WAYS` | 4 | ウェイ数(2 のべき乗)。1 は直接写像 |
| `BLOCK_BYTES` | 64 | ブロックサイズ(2 のべき乗、8 以上) |
| `FETCH_WIDTH` | 64 | CPU へ返すフェッチ幅(bit)。RV64GC の圧縮命令の切り出しは CPU 側 |
| `AXI4_ID` | 2 | fill に使う AXI ID |

既定値は 64 × 4 × 64B = **16 KiB**(Rocket `linux` と同じ)。

### 3.3 DCACHE

| パラメータ | 既定 | 内容 |
|---|---|---|
| `SETS` | 64 | セット数 |
| `WAYS` | 4 | ウェイ数 |
| `BLOCK_BYTES` | 64 | ブロックサイズ |
| `NUM_MSHR` | 2 | 未完了ミスの保持数(1 以上) |
| `NUM_WB` | 2 | 書き戻しバッファの段数 |
| `AXI4_ID_FILL` | 3 | fill に使う AXI ID |
| `AXI4_ID_WB` | 4 | 書き戻しに使う AXI ID |

既定値は 64 × 4 × 64B = **16 KiB**。

### 3.4 方式(共通、パラメータ外)

| 項目 | 方式 |
|---|---|
| 索引/タグ | 物理アドレス(PIPT) |
| 置き換え | 疑似 LRU(ツリー)。`REPLACE_RANDOM=1` で LFSR 乱数に切り替え |
| 書き込み方式 | ライトバック + ライトアロケート(DCACHE) |
| fill バースト | AXI4 INCR、`ARSIZE=3`(8 バイト)、`ARLEN = BLOCK_BYTES/8-1`、ブロック先頭から |
| 早期応答 | 要求語のビートが届いた時点で CPU へ返す(残りのビートは裏で格納) |
| 書き戻し | ブロック全体を INCR バーストで書く。`AWLEN = BLOCK_BYTES/8-1` |
| エラー | fill / 書き戻しで SLVERR/DECERR を受けたらそのラインはキャッシュせず、CPU にエラー応答を返す |

### 3.5 パラメータの制約

1. `SETS`、`WAYS`、`BLOCK_BYTES` は 2 のべき乗。
2. `BLOCK_BYTES` は 8(= `XLEN/8`)の整数倍。既定 64B = 8 ビート。
3. `NUM_MSHR >= 1`、`NUM_WB >= 1`。
4. `PADDR_WIDTH` は `CPU_TOP` の `AXI4_ADDR_WIDTH` と同じ値。
5. **`SETS × BLOCK_BYTES <= 4096`**(= ページサイズ)。アサーションで縛る。
   索引を物理アドレスで行う限り(直列 TLB)はエイリアスが起きないので原理的には
   不要だが、並列 VIPT(5.6)と SMP(6.4.7)では必須になり、既定値はちょうど上限に
   あって黙って壊れるため、最初から制約として扱う。

### 3.6 アドレスの分解

```
  PADDR_WIDTH-1                    IDX_MSB        OFS_MSB         0
 ┌──────────────────────────────┬──────────────┬─────────────────┐
 │            タグ               │  インデックス │  ブロック内オフセット │
 └──────────────────────────────┴──────────────┴─────────────────┘
   TAG_BITS = PADDR_WIDTH         IDX_BITS        OFS_BITS
              - IDX_BITS - OFS_BITS = $clog2(SETS)  = $clog2(BLOCK_BYTES)
```

既定値では OFS_BITS = 6、IDX_BITS = 6、**TAG_BITS = 40 - 6 - 6 = 28**。
タグアレイ 1 エントリ = タグ(28) + valid(1) [+ dirty(1) : D$ のみ]。
`PADDR_WIDTH` を変えるとタグ幅が自動的に追従する。

## 4. 動作仕様

### 4.1 キャッシュ対象領域

| アドレス | 扱い |
|---|---|
| `MEM_BASE` 以上 | キャッシュ対象。メモリバス(AXI4) |
| `MEM_BASE` 未満 | 非キャッシュ。周辺バス(AXI4-Lite)へ素通し |

- 非キャッシュアクセスは配列を参照せず、アクセス幅そのままで周辺バスへ出す
  (既存のデバッグバスマスタと同じレーン規則)。
- I$ も `MEM_BASE` 未満は配列を通さず周辺バスから読む(LiteX の ROM を実行するため)。
- 将来 PMA(Physical Memory Attributes)表を追加する場合も、この判定を
  差し替えるだけで済む構成にする。

### 4.2 読み出し

1. インデックスでタグアレイとデータアレイを引き、物理タグと全ウェイを比較する。
2. **ヒット**: 該当ウェイのデータを返す。
3. **ミス**: MSHR を 1 つ確保してリフィル要求を出す。
   - AXI4: `ARBURST=INCR`、`ARSIZE=3`、`ARLEN = BLOCK_BYTES/8 - 1`、`ARADDR` = ブロック先頭。
   - 要求された語が届いた時点で待っている要求へ先に返す(アーリーリスタート)。
   - ブロック全体が届いたらデータアレイとタグアレイを更新する。

### 4.3 書き込み(D$、ライトバック + ライトアロケート)

1. **ヒット**: データアレイの該当バイトのみ更新し、dirty を立てる。
2. **ミス**: ライトアロケート。ストアデータは fill のビートにマージして書き込む。
3. **追い出し**: 置換対象が dirty ならブロック全体を書き戻しバッファへ移し、AXI4 へ書き出す。
   - `AWBURST=INCR`、`AWSIZE=3`、`AWLEN = BLOCK_BYTES/8 - 1`、`WSTRB` は全バイト有効。
   - 書き戻しはリフィルと並行して進む。

### 4.4 ミス処理(ノンブロッキング、MSHR)

- ミス中も**他のライン**へのヒットアクセスは受け付ける(ヒット下ミス、ミス下ミス)。
- **同一ラインへの後続ミスは MSHR にマージ**し、バス要求は 1 回だけにする。
  ただし、該当ワードのビートが既に過ぎている場合は fill の完了を待って再実行する。
- MSHR が全て埋まっている、書き戻しバッファが満杯、退避中・fill 中のウェイに
  当たった、などの場合はその要求を待たせる。
- 応答は**要求と同じ順**で返す(ROB で整列する)。

### 4.5 AMO / LR-SC

- D$ 内で処理する。対象アドレスがキャッシュ対象領域であることを前提とする。
- **AMO**: ヒットなら読み出し→演算→書き込みを不可分に行い、dirty を立てる。
  ミスならライトアロケート後に実行する。
- **AMO のアドレスは自然整列を前提とする**(ワードかダブルワード。不整列はコアが
  先に例外にする)。そのためレーンの扱いは「アドレスのビット 2 で上半分か全体か」
  だけで、バイト位置のシフタを通さない。ヒット判定 → ウェイ選択 → 演算 →
  データ RAM への書き込みが 1 サイクルに入っており、FPGA ではここが 50MHz の
  境目だった(`LitexSystem/docs/TIMING.md` 17 章)。
- **LR/SC**: 予約レジスタを 1 組持つ(物理アドレスのブロック単位)。5.4 参照。
- 非キャッシュ領域への AMO / LR-SC は対応しない(エラー応答)。

### 4.6 フラッシュと無効化

| 操作 | 対象 | 内容 |
|---|---|---|
| `FENCE` | D$ | 未完了のバスアクセスの完了を待つ |
| `FLUSH` | D$ | dirty ラインを全て書き戻して無効化する。応答は最後の書き戻しがメモリに届いてから返す |
| `i_flush_valid` (`fence.i`) | I$ | 全ライン無効化(1 サイクル)。`i_flush_done` で完了を返す |

- fill の途中で `fence.i` が入った場合、その fill はラインを有効にしない。
- リセット直後は全ラインが無効の状態から始まる。
- ライン単位の操作(`INVAL_LINE` / `FLUSH_LINE`)は現時点では未実装。

### 4.7 デバッグアクセスの一貫性(実装済み)

デバッグ論理(SBA / Access Memory)のメモリバスアクセスは **D$ を経由する**。
周辺バス(`MEM_BASE` 未満)はこれまでどおり `DBG_BUSMST` から直接アクセスする。

| 種別 | 動作 |
|---|---|
| デバッグ読み出し | 通常のロード(`LOAD`)。ミスならラインを取り込み(次の読み出しはヒット)、CPU が書いたダーティな値もそのまま見える |
| デバッグ書き込み | **ライトスルー・ノンアロケート**(`STWTHR`)。必ずメモリへ書く。ラインがキャッシュにあればそのワードも更新するが、ダーティにはしない |
| キャッシュ対象外 | `DBG_BUSMST` から周辺バス(AXI4-Lite)へ直接 |

- 書き込みをライトスルーにしてあるので、**メモリの内容は常に最新**になる。
  デバッガが書いた命令を I$ が古いまま読むことがなく、外部から(あるいは
  テストベンチのバックドアで)メモリを見ても値が一致する。
- デバッグ書き込みのあと、CPU_TOP が **I$ を全ライン無効化**する
  (デバッガに代わって `fence.i` を実行する)。OpenOCD からブレークポイント
  命令を書いても I$ に古い命令が残らない。
- D$ の CPU ポートは `CACHE_PORT_ARB` で共有する。CPU が優先だが、デバッグ
  要求が 32 サイクル待たされたら次の調停で必ず通す(飢餓防止)。
- 経路: `DBG_DM` → `DBG_CACHE`(`RTL/CPU/CPU_DBG/DBG_CACHE/`)→ `CACHE_PORT_ARB`
  → `DCACHE`。`DBG_CACHE` は `DBG_BUSMST` と同じハンドシェイクを受け取り、
  キャッシュが応答しない場合はタイムアウトでエラーを返す。
- `CPU_TOP` / `CPU_DBG` のパラメータ `DBG_VIA_CACHE = 0` で、従来どおり
  デバッグマスタを直接バスへ出す構成にも戻せる。

## 5. CPU 側インタフェース

すべて同期式、`valid` / `ready` ハンドシェイク。応答は**要求と同じ順**で返す。

### 5.1 ICACHE

| 信号 | 方向 | 内容 |
|---|---|---|
| `i_req_valid` / `i_req_ready` | in / out | フェッチ要求 |
| `i_req_addr[PADDR_WIDTH-1:0]` | in | フェッチアドレス(`FETCH_WIDTH/8` バイト境界)。索引とオフセットはここから取る |
| `i_req_paddr[PADDR_WIDTH-1:0]` | in | 物理アドレス。タグ比較と fill に使う。5.6 参照 |
| `i_resp_valid` | out | 応答 |
| `i_resp_data[FETCH_WIDTH-1:0]` | out | フェッチデータ |
| `i_resp_error` | out | バスエラー |
| `i_flush_valid` / `i_flush_done` | in / out | 全ライン無効化(`fence.i`) |
| `i_kill` | in | 未完了の要求を捨てる(分岐予測ミス時)。fill は完了させるが応答は返さない |
| `i_cancel` | in | **ステージ 1 の要求だけ**を捨てる(`i_req_paddr` を渡しているサイクルの要求)。配列の応答もバスへのアクセスも始めない。それより前の要求には影響しない。コアが PMP に拒否されたフェッチに使う(`CPU_CORE_SPEC.md` 6.3) |

### 5.2 DCACHE

| 信号 | 方向 | 内容 |
|---|---|---|
| `d_req_valid` / `d_req_ready` | in / out | 要求 |
| `d_req_addr[PADDR_WIDTH-1:0]` | in | アドレス(アクセスサイズに整列していること) |
| `d_req_size[1:0]` | in | 0:1byte 1:2byte 2:4byte 3:8byte |
| `d_req_cmd[3:0]` | in | 5.3 の表 |
| `d_req_wdata[XLEN-1:0]` | in | 書き込み / AMO データ(下詰め) |
| `d_req_paddr[PADDR_WIDTH-1:0]` | in | 物理アドレス。タグ比較・fill・書き戻し・非キャッシュアクセスに使う。5.6 参照 |
| `d_resp_valid` | out | 応答 |
| `d_resp_data[XLEN-1:0]` | out | 読み出しデータ(下詰め、ゼロ拡張)。SC は 0:成功 1:失敗 |
| `d_resp_error` | out | バスエラー、または非対応操作 |

符号拡張は CPU 側で行う。

### 5.3 コマンド

| 値 | 名前 | 内容 |
|---|---|---|
| 0 | `LOAD` | 読み出し |
| 1 | `STORE` | 書き込み |
| 2 | `LR` | Load Reserved。予約を張る |
| 3 | `SC` | Store Conditional。成功で 0、失敗で 1 を返す |
| 4–12 | `AMOSWAP`,`AMOADD`,`AMOXOR`,`AMOAND`,`AMOOR`,`AMOMIN`,`AMOMAX`,`AMOMINU`,`AMOMAXU` | 32/64bit のみ(`d_req_size` は 2 か 3) |
| 13 | `FENCE` | 未完了のバスアクセスの完了を待つ |
| 14 | `FLUSH` | 全ラインを書き戻して無効化する |
| 15 | `STWTHR` | ライトスルー・ノンアロケート(デバッグポート用、4.7) |

### 5.4 LR/SC の規則

- 予約の単位はブロック(`BLOCK_BYTES`)。1 ハート分の予約レジスタを 1 つ持つ。
- 予約が消える条件:
  - SC を実行したとき(成功・失敗いずれも)
  - 同じブロックへの `STORE` / `AMO` / `STWTHR`(このキャッシュポートを通るもの)
  - 予約したラインが置き換え・無効化されたとき
  - `FLUSH`、リセット
- SC はアドレスが予約と同じブロックで、かつ予約が有効なときだけ成功する。
- **予約が守る範囲は 6.1 のコヒーレンシ範囲と同じ**。外部 AXI4 マスタの書き込みは
  見えない。SMP 化したときに解除条件がどう変わるかは 6.3 を参照。

### 5.5 非キャッシュ領域(`MEM_BASE` 未満)

- `LOAD` / `STORE` は配列を通さず周辺バス(AXI4-Lite)へ出す。
- **アドレスはバイト単位のまま出す**(8 バイトに丸めない)。データは 64 bit の
  レーンに置き、`WSTRB` がどのレーンかを示す。32 bit のレジスタを並べた
  スレーブ(内蔵 PLIC、CLINT)はアドレスのビット 2 で「どちらの半分か」を決める。
  丸めると、+4 のレジスタへの書き込みが落ち、+0 を読むつもりの読み出しが
  +4 の読み出し(PLIC の claim は副作用つき)と区別できなくなる。実機で
  LiteX BIOS がこれで止まった(`LitexSystem/docs/TIMING.md` 20 章)。
  LiteX の AXI-Lite → Wishbone 変換は下位 3 bit を捨てるので、外側は変わらない。
- `LR` / `SC` / `AMO` は非対応。`d_resp_error` を返す。
- ICACHE も `MEM_BASE` 未満は周辺バスから読む。

### 5.6 物理アドレスポート(MMU の差し込み口)

索引とブロック内オフセットは `*_req_addr` から、**タグは `*_req_paddr` から**
取る。これにより MMU 実装後に

- **直列**: TLB を引いてから要求を出す(2 本に同じ値を出す)
- **並列 (VIPT)**: 仮想アドレスで索引を始め、TLB 出力を次サイクルにタグとして渡す

のどちらでも、キャッシュ側を変えずに接続できる。

| 規則 | 内容 |
|---|---|
| タイミング | `*_req_paddr` は要求が受理された**次のサイクル**(ステージ 1 にいるサイクル)に有効であること。以降はキャッシュが保持するので変化してよい |
| MMU 無しの接続 | `*_req_addr` を 1 サイクル遅らせて与える(`CPU_BFM` と `SIM_CACHE` がこの形) |
| キャッシュ対象判定 | `MEM_BASE` との比較は**物理アドレス**で行う |
| 並列 VIPT の制約 | 索引 + オフセットがページ内に収まること = **`SETS × BLOCK ≤ 4096`**。既定 64 × 64B はちょうど上限 |

検証: `SIM_CACHE` セクション 15 で、要求アドレスと物理アドレスの**タグが異なる**
疑似 MMU を通し、ロード/ストア/AMO/LR-SC/命令フェッチと書き戻しが正しい物理
アドレスに対して行われることを確認している(バグ注入 M19 / M20)。

### 5.7 バス側

`CPU_CACHE` が I$ / D$ の AXI4 を `BUS_ARB` で 1 本にまとめ、`CPU_TOP` の
AXI4 / AXI4-Lite マスタポートへ接続する。デバッグ論理も同じ調停に入る。

### 5.7 CPU コア実装時の対応(参考)

CPU コア側の信号名は次のように対応させる予定:
`if_req_*` → `i_req_*`、`ls_req_*` → `d_req_*`、`ls_resp_sc_fail` は
`d_resp_data` の 0/1 で表す。MMU 実装後は仮想アドレスではなく TLB が出す
物理アドレスを `*_addr` に与える。

## 6. コヒーレンシとメモリ属性

この章は、いま何が保証されていて何が保証されていないかを明確にし、将来この
コア＋キャッシュを SMP の SoC に載せるときの手引を残すためのもの。6.1〜6.3 は
現在の仕様、6.4 は将来の設計指針(まだ実装しない)。

### 6.1 いまのコヒーレンシ範囲

**このキャッシュポートを通るマスタの集合**が、そのままコヒーレンシの範囲になる。

| マスタ | 範囲内か | 経路 |
|---|---|---|
| CPU コア | ○ | `d_req_*`(`CACHE_PORT_ARB` s0) |
| デバッガ | ○ | `DBG_CACHE` → `CACHE_PORT_ARB` s1。書き込みは `STWTHR`(4.7) |
| 外部 AXI4 マスタ(DMA、他ハート) | **×** | メモリバスに直結。D$ からは見えない |

重要なのは、**これは LR/SC に固有の弱さではない**ということ。範囲外のマスタが
書いた場所は、普通の `LOAD` でも古い値が返る。LR/SC の強さはメモリシステム
全体の一貫性の範囲とぴったり一致している。

非キャッシュ領域(`MEM_BASE` 未満)への `LR`/`SC`/`AMO` はアクセスフォールトを
返す(5.5)。黙って間違った答えを返すことはない。

### 6.2 メモリ属性

現在は `MEM_BASE` との比較 1 つで 2 種類に分けている。将来は領域テーブルに
一般化する。

| 属性 | 意味 | 現状 |
|---|---|---|
| `WB` | ライトバック + ライトアロケート | `MEM_BASE` 以上 |
| `WT` | ライトスルー + ライトアロケート。**dirty ラインが存在しない** | 未実装。`STWTHR` の機構が使える |
| `UC` | 非キャッシュ。周辺バス(AXI4-Lite)へ直接 | `MEM_BASE` 未満 |

| 属性 | `LOAD`/`STORE` | `LR`/`SC`/`AMO` | 無効化の費用 |
|---|---|---|---|
| `WB` | 配列 | 可 | dirty なら書き戻しが必要 |
| `WT` | 配列 + 書き抜き | 可 | **valid を落とすだけ** |
| `UC` | バス直行 | 不可(エラー) | 無関係 |

`WT` を入れる意味は、**無効化が安いこと**に尽きる。外部から「このラインを
捨てろ」と言われたとき、`WB` だと dirty の書き戻し経路と完了待ちが要るが、
`WT` なら valid ビットを落とすだけで済む。6.4 の probe と組にすると効く。

将来の領域テーブル(案):

```
parameter int          NUM_REGION  = 2,
parameter logic [63:0] REGION_BASE [0:NUM_REGION-1],
parameter logic [63:0] REGION_MASK [0:NUM_REGION-1],
parameter logic [1:0]  REGION_ATTR [0:NUM_REGION-1]   // 0:UC 1:WT 2:WB
```

どの領域にも当たらないアドレスは `UC` とする(現在の動作と一致する)。

### 6.3 予約(LR/SC)の規則

予約は `res_valid` + 予約ブロックのアドレスで表す。**非コヒーレント時と
コヒーレント時で解除条件が変わる**ので、両方を書いておく。

| 解除の契機 | 非コヒーレント(現在) | コヒーレント(将来) |
|---|---|---|
| SC 自身(成功・失敗とも) | ○ | ○ |
| 自ハートの同一ブロックへの `STORE`/`AMO`/`STWTHR` | ○ | ○ |
| `FLUSH`、リセット | ○ | ○ |
| **予約ブロックの置き換え(容量追い出し)** | **○** | **×(解除しない)** |
| **probe による無効化/降格** | — | **○** |

現在は「追い出したら解除」が**必要**。追い出したあとに外部が書き換え、別の
内容で読み直しても予約が生きていると、SC が成功してしまうため。

コヒーレントになると、この規則は**逆に有害**になる。他ハートが書けば必ず
probe が来るので追い出しを契機にする必要がなくなり、その一方で容量追い出しを
契機にしたままだと、他ハートと ping-pong したときに SC が永遠に失敗しうる。
RISC-V 仕様は constrained LR/SC sequence(16 命令以内、他のメモリアクセスを
含まない)の**前進を要求している**ので、これは仕様違反になる。

したがってコヒーレント版では**予約をラインの在室から切り離す**。`res_addr` を
独立に持ち、在室しているかどうかとは無関係に管理する。SC の時点でラインが
無ければ取り直すだけでよい(取り直す間に他ハートが書いていれば probe が来る)。

### 6.4 SMP 化の手引

将来、複数のコアを載せた SoC で使うときの設計指針。バスとプロトコルは SoC 側の
決めごとなのでここでは固定しないが、**どちらを選んでもこの形なら載る**という
構造だけを先に決めておく。

#### 6.4.1 何が要って何が要らないか

| 項目 | SMP で必要か | 理由 |
|---|---|---|
| D$ のコヒーレンシ(probe) | **必要** | Linux SMP の前提 |
| LR/SC の probe 連動と前進保証 | **必要** | 6.3、仕様の要求 |
| AMO の排他所有条件 | **必要** | 6.4.6 |
| 配列アクセスのアービトレーション | **必要** | 6.4.3。後から入れるのが最も高い |
| I$ のコヒーレンシ | 不要 | RISC-V は要求しない。`fence.i` + IPI(SBI)でソフトが行う |
| TLB シュートダウン機構 | 不要 | `sfence.vma` はローカル。リモートは IPI |
| ストアバッファの順序制御 | 当面不要 | コアが 1 アクセスずつ完了を待つ限り RVWMO を満たす。性能のために緩めるときに初めて `FENCE` の実装を見直す |

#### 6.4.2 外部ポート(probe チャネル)

AXI4 には probe を運ぶチャネルがない。ACE / TileLink-C / CHI のいずれかを
選ぶことになるが、**D$ 側のポートの形は共通**にできる。

| 信号 | 方向 | 内容 |
|---|---|---|
| `pb_valid` / `pb_ready` | in / out | probe 要求 |
| `pb_addr` | in | 物理アドレス(ブロック境界) |
| `pb_param` | in | 要求する遷移。0 = 無効化(toN)、1 = 共有へ降格(toB) |
| `pr_valid` / `pr_ready` | out / in | probe 応答 |
| `pr_param` | out | 遷移前の状態、データを伴うかどうか |
| `pr_data` | out | dirty だったときの書き戻しデータ(ビート単位) |

`HAS_COHERENCE = 0` のときは `pb_ready = 1`、`pr_valid = 0` で縛り、論理は
合成から落ちる。単一ハートのビルドは現在とまったく同じものになる。

**プロトコル側への必須要件**: バスは probe 応答(`pr_*`)を待たずにフィル応答を
進められること。TileLink-C(B/C/D チャネルが独立)も ACE も満たす。これが
成り立たないと 6.4.4 のデッドロック回避が組めない。

#### 6.4.3 配列アクセスのアービトレーションと複製タグ

probe が入ると、配列の要求元が増える。

| 配列 | 現在の要求元 | probe が加わると |
|---|---|---|
| タグ 読み | パイプライン s0、フラッシュ walk | + probe のヒット判定 |
| タグ 書き | フィル完了、s1(dirty セット)、フラッシュ | + probe の valid/dirty 更新 |
| データ 読み | パイプライン s0、victim 書き戻し | + probe の書き戻し |
| データ 書き | フィル、s1 ストア | — |

タグ・データとも 1R1W(7.1)なので、そのままでは競合する。対策は 2 つ。

**(1) スヌープタグの複製**

`CACHE_TAG_ARRAY` をもう 1 面置き、**書き込みは本体とまったく同じ信号で同時に
書く**。読み出しポートを probe 専用にする。これで probe のヒット判定が
パイプラインを一切止めない。

既定値での費用は `SETS × WAYS × TAG_BITS = 64 × 4 × 28 ≈ 7 kbit`。
LUTRAM か Block RAM 1 個で収まる。valid/dirty はフリップフロップなので
(7.1)複製不要で、そのまま組合せで参照できる。

**(2) 要求元をまとめる**

配列へのアクセスを、要求元ごとの `*_req_*` 信号と**1 個のアービタ**に集約する。
優先度は次のとおり。

| 優先度 | 要求元 | 理由 |
|---|---|---|
| 1 | probe | 前進保証。競合したらパイプラインを 1 サイクル止める |
| 2 | フィル完了 | 止めるとバスが詰まる |
| 3 | フラッシュ walk | 自分で進度を持っている |
| 4 | パイプライン s0/s1 | 止めてよい(`s1_can_retire` で待たせる既存の仕組みに乗る) |

**この (2) が、後回しにすると最も高くつく部分**。probe 本体を実装しなくても、
要求元を名前つきの信号に整理してアービタを 1 つ置いておけば、probe を足すのは
行を 1 本増やすだけになる。逆に、パイプラインが配列ポートを直接握る形のままだと、
DCACHE をほぼ書き直すことになる。

**実装済み(DCACHE.sv)**: 4 つの配列ポート(タグ読み/書き、データ読み/書き)は
それぞれ「要求元の `*_req` 信号 + 1 個のアービタ」の形になっていて、上の優先度表が
そのままコメントとして各ポートの頭に置いてある。probe を足すときは表に 1 行、
アービタに 1 段足すだけでよい。書き戻しキューの席は `WB_CPU_LIMIT`
(現在は `NUM_WB`、コヒーレント版では `NUM_WB - 1`)という名前で空けてある。
タグの複製は `tag_wr_*` バンドルをそのまま配線すればよい。

#### 6.4.4 probe と miss のデッドロック回避

SMP キャッシュで最も間違えやすい所。

```
probe が来たライン → そのラインのフィルが MSHR で処理中
フィルの完了        → バスの応答待ち
バス                → probe の応答待ち
```

循環する。次の 3 つを守れば閉じない。

1. **probe 応答用の資源を先に予約する。**
   `NUM_WB >= 2` を必須とし、そのうち 1 本を probe 専用に確保する。CPU 側の
   書き戻しは `NUM_WB - 1` までしか使えない。これにより、書き戻しキューが
   CPU 側の要求で満杯でも probe は必ず前進できる。

2. **処理中のラインへの probe は、フィル完了後に処理する。**
   probe を 1 個保持するレジスタを持ち、対象ラインの MSHR が処理中なら保留に
   する。保留は最長でもフィル 1 回分で、6.4.2 の必須要件(バスはフィル応答を
   probe 応答と独立に進められる)からフィルは必ず完了する。

3. **`s1_can_retire` に probe 保留を加える。**
   probe を処理中のラインは、パイプライン側から触らせない。既存の
   `ms_locked` / `s1_wait_fill` と同じ考え方で足りる。

#### 6.4.5 LR/SC の前進保証

6.3 の「予約を在室から切り離す」に加えて、**probe ロックアウト**が要る。

- `LR` を実行してから `LOCKOUT_CYCLES`(既定 64 程度)の間、**予約ブロックに
  対する probe の応答を遅らせる**。
- 遅らせるだけで、**必ず期限内に応答する**。応答しない選択肢はない(デッド
  ロックする)。
- これにより constrained sequence(16 命令以内)が 1 回は完走でき、2 つの
  ハートが互いに奪い合って両方 SC に失敗し続ける状態を避けられる。

ロックアウトが無いと、2 ハートが同じロックを取り合ったときに、双方の probe が
相手の予約を即座に割って両方が永久に失敗しうる。

#### 6.4.6 AMO の原子性の条件

現在の `AMO` は s1 で 1 サイクルの read-modify-write(4.5)。1 サイクルなので
局所的には原子的だが、SMP では条件が 1 つ増える。

> **AMO と SC は、そのブロックを排他所有(M)しているときだけ実行してよい。**

共有(S)でヒットしても実行してはならない。`s1_can_retire` に「`s1_is_amo |
s1_is_sc` なら M 状態」を加えることになる。S でヒットした場合は所有権の
取得(upgrade)を要求してから再実行する。

現在は非コヒーレントなので、在室 = 排他所有であり自明に成り立っている。
**自明に成り立っているものほど後で破られるので、条件として書いておく。**

#### 6.4.7 VIPT の制約

`SETS × BLOCK_BYTES <= 4096`(= ページサイズ)。既定値は `64 × 64 = 4096` で
ちょうど上限にあり、パラメータを増やすと黙って壊れる。

SMP + Sv39 では TLB とキャッシュを並列に引く構成(5.6)が前提になるため、この
等式は実質必須。**3.5 の制約としてアサーションで縛る。**

#### 6.4.8 システム側(キャッシュ外)

| ブロック | SMP で必要なこと |
|---|---|
| `CPU_CLINT` | `NUM_HARTS` に対応。`msip` = `0x0000 + 4 × hart`、`mtimecmp` = `0x4000 + 8 × hart`、`mtime` は全ハート共有で `0xBFF8` |
| PLIC(M6 で実装) | **最初から context 単位**(hart × 特権)で設計する。後から足すのは面倒 |
| `DBG_DM` | `hartsel` の幅、`hasel`、`haltsum`、ハートごとの halt/resume |
| ブート | hart 0 が起動し、他は `WFI` で IPI を待つ。現在の `WFI` 実装(`mip & mie` で復帰)のまま使える |
| `mhartid` | `CPU_CORE` の `HART_ID` パラメータで与える(実装済み) |

#### 6.4.9 作業順序

| 段階 | 内容 | いつ |
|---|---|---|
| 1 | VIPT 制約のアサーション、`CPU_CLINT` のマルチハート化 | **済**(2026-09-20) |
| 2 | 配列アクセスのアービトレーション化、複製タグと probe 用 `wb` エントリの席を空ける | **済**(2026-09-20) |
| 3 | メモリ属性の領域テーブル化(`WT` の追加) | DMA を入れるとき |
| 4 | 非コヒーレント DMA の対処 | Zicbom(`cbo.inval`/`clean`/`flush`)。既存の `FLUSH` 機構を 1 ライン単位にするだけで、バス改造が要らず Linux 側の対応も既にある |
| 5 | probe チャネルとコヒーレンシプロトコル | SMP の SoC を作るとき。バスの選定と同時 |

## 7. 物理実装の見積もり(Arty A7-100T)

| 用途 | 構成 | BRAM |
|---|---|---|
| I$ データ | 4 ウェイ × 4KiB | 4 タイル(ウェイごとに RAMB36) |
| I$ タグ | 64 × (4 × 29bit) | 1 タイル(または LUTRAM) |
| D$ データ | 4 ウェイ × 4KiB | 4 タイル |
| D$ タグ | 64 × (4 × 30bit) | 1 タイル |
| 合計 | | **約 10 タイル**(135 タイル中) |

Rocket `linux` の L1 が実測 12 タイル(RAMB36×8 + RAMB18×8)なので同等の規模。
容量を増やす場合(8 ウェイ 32KiB × 2)は約 20 タイルとなり、これも収まる。

### 7.1 配列は必ず Block RAM に推論させること

データ配列は **ウェイごとに別の配列**とし、書き込みはウェイをデコードした
イネーブルで行う(`generate` + `(* ram_style = "block" *)`)。

```systemverilog
for (gw = 0; gw < WAYS; gw++) begin : g_way
    (* ram_style = "block" *) logic [63:0] mem [0:WORDS-1];
    always_ff @(posedge clk)
        for (int b = 0; b < 8; b++)
            if (wr_en && wr_strb[b] && (int'(wr_way) == gw))
                mem[wr_addr][8*b +: 8] <= wr_data[8*b +: 8];
    always_ff @(posedge clk) if (rd_en) rd_w <= mem[rd_addr];
    assign rd_data[gw*64 +: 64] = rd_w;
end
```

2 次元配列を `mem[wr_way][wr_addr]` のようにウェイを可変インデックスで書くと
Vivado は RAM と認識せず、配列がすべてフリップフロップになる。
2026-09-20 のビルドはこれで **138,279 FF(Artix-7 100T は 126,800)** となり、
`place_design` が DRC UTLZ-1 で止まった。

合成ログで次の行が I$/D$ の両方に出ていることを確認する。

```
INFO: [Synth 8-3971] The signal "..._reg" was recognized as a ... RAM template.
```

`build.tcl` は合成直後に FF 数と Block RAM 数を表示し、FF が 100k を超えたら
その場でエラーにする(原因の分からない DRC エラーまで進まないようにするため)。

既定構成での目安: データ配列 8 × RAMB36(ウェイごとに 512×64bit = 32Kb)、
タグ配列 4 × RAMB18、テスト用 RAM 17 タイルで合計 30 タイル弱 / 135。

### 7.2 実測(2026-09-20、Arty A7-100T、`USE_BFM=0`)

| 項目 | 使用 | 全体 |
|---|---|---|
| Slice Registers | 6,960 | 126,800(5.5%) |
| Slice LUTs | 7,693 | 63,400(12.1%) |
| Block RAM タイル | 23 | 135(17%) |
| WNS / WHS | +4.387ns / +0.014ns(システムクロック 50MHz) | |

Block RAM の内訳は、メモリバス RAM 16 + 周辺 RAM 1 + D$ データ 4×RAMB36 +
タグ 4×RAMB18。**I$ はこのビルドでは論理合成で消える**(`USE_BFM=0` で命令
フェッチする側が居らず、デバッガは D$ しか使わないため)。CPU コアを入れると
RAMB36 が 4 個増える。

最長パスは D$ のタグ RAM 出力 → ヒット判定 → `rob_data`(12 段)で、50MHz に
対して 4.4ns の余裕がある。

### 7.3 リセットとキャッシュの内容

配列のアドレスはキャッシュの状態機械(非同期リセット)から来るため、Vivado は
`REQP-1839/1840`(RAMB async control check)を出す。リセット**アサート中**に
配列の読み書きが壊れる可能性があるという指摘だが、同じリセットでタグの valid
ビットが全クリアされるので、壊れた内容が使われることはない。

なお `ndmreset` やシステムリセットでキャッシュは空になる。デバッガの書き込みは
ライトスルーなのでメモリに残る(SIM_OCD の「RAM kept over ndmreset」はこれを
確認している)が、CPU コア実装後は、リセット前にダーティ行を書き戻したい場合
ソフトウェア側で `FLUSH` する必要がある。

| 現象 | 原因 |
|---|---|

### 8.4 概略性能(スループット)

`SIM/SIM_CACHE` の `tb_CACHE_perf.svh` が、ヒットが連続する場合とミスが連続する
場合の波形とサイクル数を出す(`make perf` で数値、`make wave-perf` で波形)。
AXI4 スレーブモデルのランダムストールは無効、既定構成(64 セット × 4 ウェイ ×
64B、MSHR 2、書き戻しバッファ 2)での測定値:

| パターン | アクセス | 定常 サイクル/アクセス |
|---|---|---|
| I$ ヒット連続 | 32 フェッチ | **1.00** |
| I$ ミス連続(1 ラインずつ) | 8 ライン | **13.0** |
| D$ ロードヒット連続 | 32 ロード | **1.00** |
| D$ ストアヒット連続 | 32 ストア | **1.00** |
| D$ ロードミス連続(fill のみ) | 8 ライン | **12.0** |
| D$ ストアミス連続(fill + ライトアロケート) | 8 ライン | **12.0** |
| D$ ミス連続(ダーティ追い出し = 書き戻し + fill) | 8 ライン | **22.0** |

- ヒットは I$ / D$ とも **毎サイクル 1 アクセス**。ロードもストアも同じで、
  同一サイクルの配列読み書きはフォワーディングで解決している。
- ミスの 12〜13 サイクルは、64B = **8 ビートのバースト**に AR とタグ更新の
  数サイクルを足したもの。要求語は届いた時点で返す(アーリーリスタート)ので、
  応答自体はこれより早い。
- ダーティ行の追い出しは、書き戻し(8 ビート)と fill(8 ビート)が直列に
  見えるため約 2 倍になる。書き戻しバッファがあるので、後続のアクセスは
  書き戻しの完了を待たない。
- 「定常」はバースト内の最初の応答から最後の応答までを (アクセス数 − 1) で
  割った値。総サイクル数にはパイプラインの立ち上がりが入る。

波形は 4 つに分けて出力し、それぞれに GTKWave のフォーマットファイルを付ける。

| ファイル | 内容 |
|---|---|
| `tb_CACHE_ihit.vcd` / `.gtkw` | I$ ヒット連続 |
| `tb_CACHE_imiss.vcd` / `.gtkw` | I$ ミス連続 |
| `tb_CACHE_dhit.vcd` / `.gtkw` | D$ ヒット連続(ロード → ストア) |
| `tb_CACHE_dmiss.vcd` / `.gtkw` | D$ ミス連続(fill → ライトアロケート → 追い出し) |

`.gtkw` は `gen_gtkw.py` が生成する。信号は「CPU 側」「ステージ1(ヒット判定)」
「配列」「MSHR / fill」「書き戻し」「ROB」「AXI4」「BUS_ARB」…とグループ分けし、
状態機械は名前で表示する(`gtkw_filter/*.txt`)。テストベンチが書き出した
`tb_CACHE_*.marks` の時刻がマーカになるので、各バーストの先頭にすぐ飛べる。

```
cd SIM/SIM_CACHE
make perf            # 数値だけ
make wave-perf       # VCD 4 本 + .gtkw を生成
make gtkwave-dmiss   # GTKWave で開く(ihit / imiss / dhit / dmiss)
```

### 8.5 FPGA での確認(2026-09-20、Arty A7-100T 実機)

`FPGA/ARTY_A7_100T/openocd/cache_test.tcl` を JTAG 経由の OpenOCD から実行し、
**CACHE TEST RESULT : PASS**。確認した内容:

| # | 内容 |
|---|---|
| 1 | 1 ライン: 書き込みミス → 読み出しミス(ライン確保)→ 読み出しヒット → 同一ライン内の別ワードのヒット → 書き込みヒット |
| 2 | 別セットの 8 ライン |
| 3 | 32KiB の `load_image` / `verify_image`(全セットが 2 周入れ替わる)。そのあと 1., 2. のアドレスを読み直して値が正しいこと |
| 4 | `reset halt` 後もメモリの値が残っていること(デバッグ書き込みがライトスルーである証拠) |
| 5 | 周辺バス(非キャッシュ)のアクセス |

電源を入れたまま繰り返し実行しても PASS する(`reset halt` でキャッシュは空に
なるが RAM は保持される)。

`verify_image` 実行時の `No working memory available` / `not enough working
area` は想定どおり。OpenOCD はターゲット上で CRC ルーチンを実行しようとする
が、コードを実行できるハートがまだ無い(`progbufsize=0`)ため、JTAG 経由で
全データを読み戻す方式にフォールバックする。CPU コア実装まで work area は
設定しないこと。

CPU コア実装後は、コアからのアクセスとデバッガからのアクセスの一貫性(4.7)を
実機でも確認する。

## 9. 決定事項

| # | 項目 | 決定 |
|---|---|---|
| 1 | 既定構成 | Rocket `linux` と同等(I$ / D$ とも 16KiB = 64 セット × 4 ウェイ × 64B) |
| 2 | パラメータ化 | セット数・ウェイ数・ブロックサイズを I$ / D$ 別に指定可能 |
| 3 | アドレス幅 | CPU 設定に合わせる(`PADDR_WIDTH`、既定 40) |
| 4 | 索引方式 | PIPT(MMU 実装後もエイリアス制約なし) |
| 5 | I$ フェッチ幅 | 64bit |
| 6 | D$ MSHR | 既定 2、パラメータ化 |
| 7 | 非キャッシュ領域 | `MEM_BASE` 未満は周辺バス(AXI4-Lite)へ。AMO/LR/SC は非対応 |
| 7b | アドレスポート | 索引用 `*_req_addr` とタグ用 `*_req_paddr` に分離。直列 / 並列 VIPT のどちらでも接続できる |
| 8 | 置き換え | 疑似 LRU(既定)。パラメータで乱数に切り替え |
| 9 | 書き込み | ライトバック + ライトアロケート |
| 10 | デバッグ一貫性 | デバッガのメモリバスアクセスは D$ 経由。読み出しはアロケート、書き込みはライトスルー・ノンアロケート、書き込み後に I$ を無効化 |
| 11 | L2 キャッシュ | 本フェーズでは実装しない |
| 12 | コヒーレンシ範囲 | このキャッシュポートを通るマスタ(コア + デバッガ)まで。外部 AXI4 マスタは見えない。LR/SC も通常のアクセスも同じ範囲(6.1) |
| 13 | SMP への備え | probe チャネル本体とプロトコルは作らない。**配列アクセスのアービトレーション化と VIPT 制約だけ先にやる**(6.4.3、6.4.7)。後から入れるのが最も高い部分だから |
| 14 | 非コヒーレント DMA | snoop バスではなく Zicbom(`cbo.inval`/`clean`/`flush`)で対処する。既存の `FLUSH` 機構を 1 ライン単位にするだけで済み、バス改造も Linux 側の新規対応も要らない(6.4.9) |
| 15 | 予約と在室の関係 | 非コヒーレント時は「追い出しで解除」が**必要**、コヒーレント時は「追い出しでは解除しない」に**変える**(6.3)。前進保証のため |

## 10. Rev-1(設計計画)からの変更

| 項目 | Rev-1 の計画 | Rev-2(実装) | 理由 |
|---|---|---|---|
| 索引方式 | VIPT(`SETS × BLOCK_BYTES <= 4096` 制約) | **PIPT** | MMU は次フェーズであり、キャッシュは物理アドレスを受け取る。PIPT ならエイリアス制約が無く、セット数を自由に増やせる |
| モジュール分割 | `CPU_ICACHE` / `CPU_DCACHE` / `CPU_CACHE_ARRAY` / `CPU_CACHE_MSHR` / `CPU_CACHE_BUS` | `ICACHE` / `DCACHE` / `CACHE_TAG_ARRAY` / `CACHE_DATA_ARRAY` / `CPU_CACHE` | MSHR とバス制御は D$ の状態機械と密結合で、分けると却って読みにくい。配列はタグとデータで役割が違うので分けた |
| D$ MSHR 既定 | 4 | **2** | Rocket 相当の規模で十分。パラメータで増やせる |
| I$ の MSHR | 2 | 1(ミスは 1 つずつ) | 命令フェッチは順次で、早期応答があれば実効差が小さい |
| AXI4 ID | D$ は MSHR ごとに別 ID | fill と書き戻しで別 ID(3 / 4)、I$ は 2 | 同一 ID で順序保証させるほうが単純で、MSHR の特定は内部状態で足りる |
| 置き換え既定 | RANDOM | **疑似 LRU**(乱数はパラメータ) | ヒット率が良いほうを既定にした |
| フラッシュ操作 | 全体 + ライン単位 | 全体のみ(`FENCE` / `FLUSH` / `fence.i`) | ライン単位は Zicbom と併せて将来追加する |
| デバッグのキャッシュ経由化 | 本フェーズ(ヒット時はラインを更新してダーティ) | 本フェーズ(書き込みは**ライトスルー**) | ダーティのままだとメモリが古くなり、I$ のフィルや外部から見た値がずれる。ライトスルーなら一貫性を保ったままヒット/ミスの効果も確認できる |
| 置き場所 | `RTL/CPU/CPU_CACHE/` | 同左(一度 `RTL/CPU/CPU_CACHE/` に置いたものを統合) | `CPU_TOP` 配下にインスタンス化されるため |
