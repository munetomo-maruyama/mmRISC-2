# 性能測定(2026-10)

[English](BENCH.md)

CoreMark と Dhrystone を、(1) シミュレーション(`SIM/SIM_SYS`、マシンモード、
コア + 実キャッシュ)と (2) 実機(Arty、50 MHz、Linux のユーザプログラム)で測る。
シミュレーションでは計時部分のサイクル数と命令数が正確に分かり、どこでサイクルを
失っているかを数えられる。実機の数字はメモリ(DDR3)と OS を含んだ実力。

| 環境 | 作り方 | 走らせ方 |
|---|---|---|
| シミュレーション | `SIM/SIM_SYS/bench/`(C ライブラリなし、CoreMark の `ee_printf`) | `cd SIM/SIM_SYS && make bench` |
| 実機 | `LitexSystem/software/bench/`(静的リンク、glibc) | `software/bench/README.md` |

### ビルドの条件

コンパイラはどちらも **GCC 13.2.0**(riscv-gnu-toolchain、`gc891d8dc23e`、`/opt/riscv`)。
最適化は **`-O2` だけ**で、`-O3`・`-funroll-loops`・`-finline-functions` などの、CoreMark の
公表値でよく使われるオプションは付けていない。チューニングはツールチェーンの既定の
`-mtune=rocket`(指定していない)。

| | 実機(`LitexSystem/software/bench/`) | シミュレーション(`SIM/SIM_SYS/bench/`) |
|---|---|---|
| コンパイラ | `riscv64-unknown-linux-gnu-gcc` 13.2.0 | `riscv64-unknown-elf-gcc` 13.2.0 |
| アーキテクチャ | `-march=rv64imafdc -mabi=lp64d`(`coremark` / `dhrystone`)<br>`-march=rv64imafdc_zba_zbb -mabi=lp64d`(`coremark_zb` / `dhrystone_zb`、11 章) | `-march=rv64imafdc_zicsr_zifencei -mabi=lp64d`(11 章の比較では `_zba_zbb` を足した) |
| 最適化 | `-O2` | `-O2` |
| その他 | `-static`(glibc 2.40 を静的リンク。C ライブラリ自体は rv64gc) | `-mcmodel=medany -nostdlib -fno-tree-loop-distribute-patterns`(C ライブラリなし。`memset` などは自前の `minilib.c`) |
| CoreMark | posix の移植をそのまま、`-DITERATIONS=0 -DPERFORMANCE_RUN=1`(10 秒以上走る回数を自分で選ぶ) | `-DITERATIONS=10 -DPERFORMANCE_RUN=1`、`ee_printf` で `tohost` へ出力 |
| Dhrystone | riscv-tests の Dhrystone 2.2、`-std=gnu89 -fno-common -fno-builtin-printf -w`。計時は `bench_usec()`(マイクロ秒)、2 秒未満なら回数を 10 倍にして測り直す | riscv-tests の Dhrystone 2.2、500 回、計時は `mcycle` |

CoreMark は実行時に、使ったコンパイラとオプションを自分で表示する(`Compiler version :
GCC13.2.0`、`Compiler flags : -march=rv64imafdc -mabi=lp64d -O2 -static`)。

Dhrystone の文字列関数(`strcpy` / `strcmp`)は、実機では glibc の語単位の版、
シミュレーションでは自前の 1 バイトずつの版を使う。同じ Dhrystone でも両者の数字が
離れる(シミュレーションのほうが低い)のは主にこのため(2 章、10 章)。

### どこでサイクルを失っているか(発行点 ID → EX で数えたもの)

`+profile` の「where an instruction is issued」。各サイクルは、命令を EX へ発行したか、
発行できなかった理由のどれか 1 つに数えられ、合計が総サイクルになる。

| | CoreMark | Dhrystone |
|---|---|---|
| 発行した | 61.5 % | 47.5 % |
| **EX 停止: MA が D$ の応答待ち** | **23.6 %** | **33.8 %** |
| 分岐予測ミス(リダイレクト + 詰め直し) | 6.6 % | 11.2 % |
| EX 停止: MDU / FPU | 4.8 % | 4.3 % |
| EX 停止: ロードユース | 3.5 % | 3.2 % |
| その他(フェッチ、直列化、変換) | 0.0 % | 0.0 % |

| 予測ミス / 実行 | CoreMark | Dhrystone |
|---|---|---|
| 条件分岐 | 82,387 / 582,985(14 %) | 3,506 / 28,002(13 %) |
| `jal` | 7,996 / 43,640(18 %) | 6,008 / 8,503(**71 %**) |
| `jalr`(主に関数の戻り) | 7,055 / 21,377(33 %) | 4,008 / 7,003(57 %) |
| 1 回の予測ミスの損失 | 約 3.9 サイクル | 約 3.5 サイクル |

### 読み取れること

1. **D$ のヒットでも、ロード / ストア 1 回ごとに約 1 サイクル止まる**(最大の損失、
   23〜34 %)。D$ は毎サイクル 1 アクセスを受けられる(`CPU_CACHE_SPEC.md` 8 章)が、
   要求から応答までは 2 サイクルかかる。コアは MR で要求を出し、命令が MA にいる
   次のサイクルに応答を待つので、MA が 1 サイクル待ち、後ろの命令もすべて止まる。
   データアクセス 1 回あたりの停止は 1.08〜1.12 サイクルで、ほぼ全部がこれ。
2. **`jal` と `jalr` の予測ミスが多い**。`jal` の飛び先は命令そのものに書いてあるのに、
   BTB(64 エントリ、直接写像)に無いと EX まで分からない。関数の戻り(`jalr`)は
   呼び出し元ごとに飛び先が変わるが、戻りアドレススタックが無い。
3. MDU(乗算 3 サイクル、除算 32/64 サイクル)が 4〜5 %。

### 1 つだけシミュレーションと合わなかった数字 → 分岐予測の置き場所の制約

`micro` の整列ロードのループ(4 命令、全部 D$ ヒット)が実機で 10.5 サイクル / 回、
シミュレーションでは 6.3 だった。同じ命令列を両方で走らせて切り分けた(`loops.h`、
`micro 50 loops` / `sweep`、`SIM/SIM_SYS/bench/ldloop.c`):

| ループ | 分岐の番地 | 8 バイト語内の位置 | 実機 | シミュレーション |
|---|---|---|---|---|
| ロードなし | — | — | 4.56 | 4.29 |
| `ld` 同じ語 | 0x10d8e(2 バイトの `c.bnez`) | 6 | 6.59 | 6.32 |
| `ld` ストライド 8 | 0x10d4c | 4 | 6.62 | 6.42 |
| `ld` ストライド 64(`loops`) | 0x10d9e | **6(後半が次の語)** | **10.81** | 6.31 |
| `ld` ストライド 64(`sweep`、64 ライン) | 0x1097a | 2 | 6.58 | 6.19 |

キャッシュでもページングでもなく(4 KiB ページの 3 段のページテーブルでもシミュレーションは
6.30)、ループの **32 bit の分岐が 8 バイトのフェッチ語の最後の 2 バイトから始まり、後半が
次の語に掛かっている**ことが原因だった。BTB はこの位置の分岐を予測しない
(`CPU_CORE_SPEC.md` 決定 33・34)ので、毎回予測ミスになり、約 4.5 サイクル失う。
シミュレーションのループは、たまたま分岐が語の中に収まる位置にあった。

C 拡張のコードでは 32 bit 命令の開始位置が 2 バイト単位でばらつくので、この位置に来る
分岐は珍しくない。プロファイルで数えると:

| | CoreMark | Dhrystone |
|---|---|---|
| 語をまたぐ 32 bit の分岐 / `jal`(実行数) | 171,935 / 626,625(27 %) | 6,001 / 36,505 |
| そのうち予測ミス | 52,164 = **予測ミス全体の 54 %** | 4,501 = 33 % |
| 損失(× 約 3.9 サイクル) | 総サイクルの約 3.5 % | 約 4 % |

## 3. 改善の候補(効果の大きい順)

| 候補 | 見込み | 規模 | 内容 |
|---|---|---|---|
| A. D$ ヒットで MA を止めない | CoreMark 最大 +31 %、Dhrystone 最大 +51 % | 大 | 応答を 1 サイクル早める(BRAM の出力からウェイ選択まで 1 サイクルに入れる。タイミングが厳しい)か、ロードの結果を MA の 1 サイクル後に書く形にする(ロードユースの間隔が延び、バスエラーの精密例外の扱いを決め直す必要がある) |
| B. 語をまたぐ 32 bit の分岐も予測する | CoreMark 約 +3.5 %、Dhrystone 約 +4 % | 中 | 決定 34 の制約を外す。予測を、分岐の後半が入っている次の語で使う(または前半の語のエントリが次の語のフェッチを待ってから飛ぶ) |
| C. `jal` を ID で飛ばす + 戻りアドレススタック | CoreMark 約 +1 %、Dhrystone 約 +9 % | 中 | `jal` は飛び先が即値なので ID でリダイレクトでき、BTB 外れでも 1〜2 サイクルで済む。`jalr` の戻りは小さなスタックで当てる。B と重なる分がある(語をまたぐ `jal`) |
| D. 乗算器の短縮 | 数 % | 小〜中 | 3 サイクル → 2 サイクル(DSP のパイプライン) |
| E. 不整列アクセスのハードウェア対応(課題 6) | 普通のコードでは 0 | 大 | 1 回 1629 サイクルを数サイクルにする。不整列アクセスを多用するコード(パケット処理など)でだけ効く |

見込みは、その分の停止がそのまま消えると仮定した上限(A は D$ 待ちの全部、B は語をまたぐ
分岐の予測ミスの全部、C は `jal` / `jalr` の予測ミスの全部)。

## 4. B と C の結果(2026-10-02、シミュレーション)

B(ワードをまたぐ 32 bit の分岐を次のワードの tail エントリで予測)、C のうち戻り
アドレススタック(8 段、フェッチ側と実行側の 2 本)、BTB を 64 → 256 エントリ。
`CPU_CORE_SPEC.md` 4.2、決定 56・57。

| | 前 | 後 | |

| CoreMark サイクル | 5,834,958 | 5,684,843 | **+2.6 %**(1.759 CoreMark/MHz) |

| Dhrystone サイクル | 426,006 | 396,032 | **+7.6 %**(0.72 DMIPS/MHz) |

BTB の大きさだけを変えると(B + スタック込み):

| BTB | CoreMark | Dhrystone |
|---|---|---|
| 64 | 5,701,143 | 410,008 |
| 256 | 5,684,843 | 396,032 |

`jal` を ID で飛ばす案は入れなかった。残る `jal` の予測ミスは Dhrystone で 1 回あたり
約 4 回、EX で直すより 1 サイクル早くなるだけなので、効果は 0.5 % 程度。

残る予測ミスの主は CoreMark の条件分岐(9.3 %、2 bit カウンタ)。履歴付きの予測器
(gshare など)で半分にできれば 2 % 前後。

検証: `t24_predict`(ワードをまたぐ分岐、tail の誤用、2 か所からの呼び出し、戻りの間の
予測ミス、スタックより深い再帰。各部を同じ命令列の参照と比べて 1.25 倍以内)、
変異 M233〜M239 すべて検出、M174・M177・M180 は新しい行に合わせて更新(M175 は以前から
見えないもの)。SIM_CORE 全試験・背圧・Icarus、riscv-tests p / v、SIM_SYS、BIOS、
SD モデルからの Linux 起動。

## 7. 乗算の短縮(2026-10-03、シミュレーション)

`CPU_CORE_SPEC.md` 決定 61。MUL / MULW の EX の待ちを 3 → 1 サイクル、MULH 系を 3 → 2 に。

| | 前 | 後 | |
|---|---|---|---|
| CoreMark(10 回) | 4,312,829 サイクル | **4,124,913** | **+4.6 %、2.42 CoreMark/MHz**(CPI 1.149) |
| CoreMark の EX 停止: MDU | 281,880(6.5 %) | 93,960(2.3 %) | 乗算 93,960 回 × 1 |
| Dhrystone(500 回) | 253,069 | 252,069 | +0.4 % |

Dhrystone の MDU 待ち(17,195 サイクル、6.8 %)は約 500 回の**除算**(1 回 34 サイクル前後)で、
乗算の短縮は効かない。除算の早期終了(被除数の先頭の 0 を飛ばす、Rocket の
`divEarlyOut` 相当)で縮められる。

実機(2026-10-03、配置配線後 WNS +0.162 ns): **2.313 CoreMark/MHz**(2.213 から +4.5 %)、
1.302 DMIPS/MHz(+0.3 %)。シミュレーションの比のとおり。

**カーネルが主の負荷は 1.2〜1.7 倍**になった。見込み(`CPU_L2_SPEC.md` 1 章、1.23〜1.37 倍)を
上回り、`tftp` 1.66 倍、`ext4read` 1.56 倍、`sdread` 1.50 倍、`ls` 1.46 倍。理由は L2 のヒット率が
見込みの 6〜8 割より高く、**85〜95 %** あったこと(カーネルのコードとよく使うデータが 256 KB に
収まる)。L1 のミス 1 回の重さ(フロントエンドが空 ÷ I$ ミス、D$ 待ち ÷ D$ ミスで見積もる)は:

|---|---|---|

| D$ ミス 1 回(`ls` / `tftp`) | 44 サイクル | **21〜22 サイクル** |
| D$ ミス 1 回(`sdread` / `ext4read`) | 62〜63 サイクル | 34〜41 サイクル |

I$ のミスは L2 のヒット(AR から 1 ビート目まで 2 サイクル + L1 の fill)にほぼ下がった。
`sdread` / `ext4read` の D$ 待ちはあまり減っていない(38.8 %、30.7 %)。SD カードの DMA は D$ を
通る書き込み(ライトスルー)で、L2 では一部の書き込みとしてメモリへ素通しになり、1 回ずつ
メモリの応答を待つ。その間 D$ が塞がるのが残っていると見ている(確かめていない)。L2 で DMA の
書き込みを受け止める(行ごと確保する、応答を先に返す)と減る見込み(`CPU_L2_SPEC.md` 8 章)。

`forkexec` はヒット率 58 % と低い。fork と exec のたびに新しいページ(ページテーブル、コピーした
ページ、新しいプロセスのデータ)を触るので、初めての行が多い。`md5sum`(71 %)は一度しか読まない

## 16. FPU のパイプライン化(C2、2026-10-09、実機)

コアの `CORE_FPU` を `FPU_PIPE` に入れ替えた版(`CPU_CORE_SPEC.md` 10.11、配置配線後 WNS
+0.286 ns、スライス 89.0 %、`TIMING.md` 33 章)。`micro` にアセンブラの核
(`software/bench/fpkern.S`)を足し、`micro 50 fp` で浮動小数点だけを測れるようにした。

**`micro`(積和 1 回あたりのサイクル数)**。SIM_SYS は `SIM/SIM_SYS/bench/fploop.c` で同じ核を
走らせた値(行列は 16×16 で D$ に入る)。「前の版」は同じ fploop を段階 2 の前の RTL
(4cb3603)で走らせた値:

| | 実機(64×64 など) | SIM_SYS | SIM_SYS 前の版 | 速さ(SIM_SYS) |
|---|---|---|---|---|
| dgemm、アセンブラ 4×4 | **4.05**(24.7 MFLOPS) | 2.18 | 11.19 | 5.1 倍 |
| FIR 8 タップ、アセンブラ | **1.52**(65.7 MFLOPS) | 1.45 | 10.10 | 7.0 倍 |
| 内積、アセンブラ | **3.66**(27.3 MFLOPS) | 3.66 | 12.81 | 3.5 倍 |
| dgemm、C(`-O2`) | 18.6 → 修正後 **16.6**(6.02 MFLOPS) | 17.60 → **15.67** | 16.73 | |

- **FIR は目標の 1 サイクルピッチにほぼ届いた**(1.52、65.7 MFLOPS。段階 2 の前の C の dgemm
  5.69 MFLOPS の 11.5 倍。積和 64 本に FLD 8 本・FSD 8 本・
  ループ 3 本を足した 83 本 ÷ 64 = 1.30 が発行の下限)。実機でも D$ に入るので SIM_SYS と同じ。
- **内積は FLD 2 本 / 積和で決まる**(3.66、実機も SIM_SYS も同じ)。
- **dgemm のアセンブラは実機で 4.05**(SIM_SYS の 2.18 から伸びた)。64×64 の 3 行列(96 KB)は
  D$(16 KB)に入らず、4 列のブロックごとに B 全体(32 KB)をなめるので、B の行がそのたびに
  L2 から来る。修正後の C 版(16.6)の 4.1 倍、段階 2 の前の C 版(17.6)の 4.3 倍。さらに速くするには B のパネルを
  D$ に収まる大きさに切る(キャッシュのブロッキング)のが次の手で、FPU の話ではない。
- 内積・FIR の結果は C と一致(`answers agree with C`)。CoreMark 2.497 / 2.785(Zba・Zbb)、
  Dhrystone 1.489 / 1.497 で 15 章(2.498 / 2.786、1.488 / 1.496)と変わらない。帯域・依存ロード・
  不整列ロード・4 命令のループも変わらない。

**C の dgemm が 17.6 → 18.6 と遅くなっていた(段階 2 のバグ、修正済み)**。内側のループは
`fld c; fld b; addi; addi; fmadd; fsd; bne` の 7 命令で、`fsd` が `fmadd` の答えを EX で待つ。
LSU は EX からアクセスを先出しする(`lsu_e_valid`)が、その条件に「FPU の答えを待っていない」が
なく、待っている `fsd` が古いデータのまま D$ に要求を出していた。要求は次のサイクルで取り消され
(答えは正しい)、そのあと `ex_e_blocked` で **EX からではなく MA から**出るので、答えが来てから
2 サイクル遅れた。前の版は `fmadd` 自身が EX を占めていたので `fsd` が先に EX に来ることがなく、
この穴は見えなかった。トレースで 1 周 16 → 17 サイクル(前の版 → 段階 2)、`fmadd` のリタイアから
`fsd` のリタイアまで 11 サイクル(FP の依存の 9 に対して +2)。`lsu_e_valid` に `~fp_wait` を足して
**1 周 15 サイクル**、SIM_SYS の C dgemm は 17.60 → 15.67(前の版の 16.73 より速い)。
**実機でも 18.6 → 16.6**(見込み 16.7)になり、段階 2 の前(15 章の 17.6)より 6 % 速い。
修正後のビットストリーム(WNS +0.113 ns、`TIMING.md` 34 章)で `bench.sh` も回し直し、
CoreMark 2.498 / 2.785、Dhrystone 1.488 / 1.496、アセンブラの核(4.04 / 1.52 / 3.66)と
ほかの `micro` の値は修正前と同じ。

答えが変わらずサイクルだけ失うバグは、試験でもバグ注入でも見えなかった。`fploop` に核ごとの
サイクルの上限(いまの値の約 5 % 上)を入れ、超えたら失敗にした。SIM_SYS の `bug_inject.sh` は
`fploop` も走らせ、この穴を戻す変異(M19)を検出する。

**行列積のキャッシュのブロッキング**(2026-10-09、`software/bench/fpkern.c`、SIM_SYS)。
`fpk_dgemm4` は 4 行ごとに B 全体(n = 64 で 32 KB、D$ の 2 倍)をなめるので、B が毎回 L2 から
来る。B を KC 行 × NC 列のパネルに切って D$ に置き、A の 4 行ずつをその前に通す:

- **B のパネルは詰め直す**(packing)。核が 1 つの k で読む 4 個を 32 バイトに並べ、セットの
  衝突もなくす。
- **A は詰め直さない**。最初は A の 4 行も詰め直したが、C の 1 要素ずつの写しが 4,096 要素 ×
  パネルの数だけ走り、命令が 1 積和あたり 2.03 本(核だけなら 1.59)になった。核に A の 4 行を
  4 本のポインタで直接読ませ(2 つの k ごとに足し算 4 本、1 積和あたり約 0.1 本)、パネルの幅を
  まとめて 1 回で呼ぶ(`fpk_mm4xn`)ようにして 1.79 本になった。
- **残りは D$ のミス**。MA はミスの応答を待つので、ミスは計算と重ならない。A はパネルの列ごとに
  (n / NC 回)、C は行ごとに(n / KC 回、読みと書き戻し)読み直される。パネルを 8 KB(D$ の
  半分)に保つと、どの切り方でもミスの数がほぼ同じになる。

| KC × NC(パネル) | SIM_SYS、n = 64 |
|---|---|
| ブロッキングなし(`fpk_dgemm4`) | 3.25 |
| 32 × 32(8 KB)、A も詰め直す版 | 2.46 |
| **64 × 16(8 KB)** | **2.23** |
| 32 × 32(8 KB) | 2.24 |
| 16 × 64(8 KB) | 2.46 |
| 64 × 20 / 24(10 / 12 KB) | 2.30 |
| 64 × 28 / 32(14 / 16 KB) | 2.39 / 2.46 |

64 × 16 を既定にした(C を 1 回しか読み書きしない)。SIM_SYS の 3.25 → 2.23 は 1.46 倍。

**実機(`micro 50 fp`)**:

| dgemm 64×64 | 積和 1 回あたり | MFLOPS |
|---|---|---|
| C(`-O2`)、段階 2 の前(15 章) | 17.6 | 5.69 |
| C(`-O2`) | 16.6 | 6.04 |
| アセンブラ 4×4、ブロッキングなし | 4.01 | 24.9 |
| **アセンブラ、ブロッキング** | **2.42** | **41.2** |

ブロッキングで 1.66 倍(SIM_SYS の 1.46 倍より大きい。実機のミスのほうが重いので、ミスを減らした
効きも大きい)。SIM_SYS の 2.23 との差 0.19 がミスの重さの差。C2 の前の C の dgemm からは
**7.2 倍**。50 MHz で 41 MFLOPS は、FLD と FMADD を 1 本ずつしか発行できないこのコアで核が
出せる上限(約 1.7)の 7 割。`fploop` には 32×32 の
ブロッキング版(24 KB で D$ に入らない、2.40、上限 2.52)を足した。

## 17. 最大の最適化での CoreMark と Dhrystone(2026-10-09)

これまでの値は比較の条件をそろえるため `-O2`(と Zba / Zbb)で作ったもの。それと並べて、
このコアで一番速くなるオプションで作ったものも測る(`software/bench/README.md`「最大の最適化」)。

**オプションの選び方**: `SIM/SIM_SYS/bench/optsweep.sh` が CoreMark(10 回)と Dhrystone(500 回)を
10 通りのオプション × rv64gc / Zba・Zbb で作り、SIM_SYS で走らせてサイクルから比べる。
CoreMark の答え(`crcfinal` 0xfcaf)はどれも同じ。SIM_SYS の Dhrystone は文字列関数が自前の
簡単なもの(実機は glibc)なので値は実機より低く、見るのは順位:

|---|---|---|---|---|
| `-O2`(これまで) | 2.558 | 2.845 | 1.282 | 1.288 |
| `-O3` | 2.673 | 2.986 | 1.297 | 1.300 |
| `-O3 -funroll-loops` | 2.669 | 2.991 | 1.312 | 1.324 |
| **sf** = `-O3 -funroll-all-loops -finline-functions --param max-inline-insns-auto=20 -falign-{functions,jumps,loops}=4` | **2.739** | **3.084** | 1.314 | 1.276 |

- **`-O2 -flto` の Dhrystone(+17 %)は規則の外**。Dhrystone の規則(`dhrystone.h`: 分割コンパイル、

## 18. メモリの待ちの内訳(M0、2026-10-10、シミュレーション)

`ROADMAP_J.md` の M0: M1〜M4 のどれをやるかを決める前に、どんな待ちがあるかを数える。そのために足したもの
(`CPU_CORE_SPEC_J.md` 決定 71):

- **PMU のイベント 20〜24**: MA がストアで待つ、MA が待つ間に D$ がミスを処理している、ライン読み込みが
  1 本以上 / 2 本以上未完了、MA が待つ間に D$ がダーティな追い出し行を写している。`software/bench/workload.sh`
  が実機で数える(1 つの負荷につき 2 回の実行を足し、2 つ目の表「メモリの待ち」を出す)。
- **SIM_SYS のプロファイラ**(`make profile`、`make bench`): MA の待ちをアクセスの種類ごと、アクセスごと
  (読み込みを頼む前 / 未完了の間 / その後)に分け、退役した各ロードから値を最初に読む命令までの距離
  (退役した命令を `CORE_DECOMP` + `CORE_DEC` の写しでもう一度デコードする)、サイクルごとの未完了の読み込みの
  数を出す。

| | サイクル | MA の待ち | ミスで: ロード / ストア | 追い出し行の写し | ミスしたロードを 1 / 2 命令後に使う | M4 で隠せる上限 | 読み込み 2 本未完了 |
|---|---|---|---|---|---|---|---|
| CoreMark | 3,908,920 | 178(0.005 %) | 0 / 129 | 0 | ― | ― | 27 サイクル |
| Dhrystone | 221,979 | 0 | 0 / 0 | 0 | ― | ― | 0 |
| `t19_ldbench`(C、リスト、整列) | 56,954 | 1,336(2.3 %) | 25 / 1,172 | 0 | 1 本中 1 / 0 | 0 % | 26 サイクル |
| `ldloop`(micro のループ、U モード) | 88,459 | 4,967(5.6 %) | 4,335 / 294 | 1,830 | 355 本中 13 / 341 | 7.5 % | 0 |
| `fploop`(FP カーネル、dgemm) | 613,197 | 82,124(13.4 %) | 28,378 / 41,550 | 22,040 | 2,803 本中 16 / 587 | 38.7 % | 123 サイクル |

「M4 で隠せる上限」: ミスしたロードが待ったサイクルのうち、ロードとその値を最初に使う命令の間の命令が
1 サイクル 1 命令で埋められる分(使うまで止めない方式の上限)。

**分かったこと**

1. **CoreMark と Dhrystone にはメモリの待ちが無い**(L1 に収まる)。M1〜M4 の効果は収まらない負荷で見る
   必要がある: シミュレーションでは `fploop` と `ldloop`、実機では 14 章の Linux の負荷(D$ 待ち 12〜40 %)を
   新しいイベントで。
2. **ダーティな追い出し行の写しが大きい**: `fploop` で待ち 82,124 サイクルのうち 22,040(27 %)、`ldloop` で
   4,967 のうち 1,830(37 %)。追い出す行がダーティだと、D$ の読み込みエンジンはまずその 8 語を書き戻し
   バッファに写し(`F_WB_READ` → `F_WB_WAIT` → `F_WB_PUSH`、約 11 サイクル)、それから新しい行を頼む。先に頼んで、
   読み込みが未完了の間に写せば隠せる: 写しは読み出しポートから 1 サイクル 1 語、読み込みは書き込みポートから
   1 サイクル 1 ビートで、最初のビートはアドレスから早くても 2 サイクル後なので、写しが常に先を行く。
   いちばん安い重ね合わせ(`ROADMAP_J.md` の候補 M5)。
3. **ストア**: ミスするとロードと同じだけ待つ(1 回 16〜31 サイクル、write-allocate)。`fploop` ではミスでの
   待ちの 59 %(C の書き戻し)、`t19_ldbench` ではほぼ全部。これを取り除くのが M1(ストアバッファ)。
4. **ミスしたロードはたいていすぐ使われる**: `ldloop` では 355 本中 341 本が 2 命令後に使われ(ポインタを
   たどる、和を取る)、M4 で隠せるのは待ちの 7.5 % まで。`fploop` は行列のカーネルが先読みしているので
   39 % まで。M4 は先にロードしておくコードに効き、値をすぐ使うコードにはプリフェッチ(M2 / M3)が効く。
5. **ミスが 2 つ同時にあることはまれ**(最大でサイクルの 0.02 %)で、**そもそもバスは 1 度に 1 本の読み出し
   しか扱わない**: `CPU_CACHE` の調停器は読み出しを最後のビートまで離さず、L2 も 1 度に 1 件しか受けないので、
   D$ に MSHR が 2 つあっても 2 つ目のミスは 1 つ目の後ろで待つ。M3 / M4 が重ねるのはミスと計算であって、
   ミスどうしではない。ミスどうしを重ねるにはバス側も要る。

実機の数字は 18.1。
