# Arty A7-100T 合成結果の解析（第 1 回ビットストリーム）

対象: `LitexSystem/build/gateware/` 2026-09-21 の Vivado 2025.1 実行
デバイス: xc7a100tcsg324-1 / システムクロック 50 MHz (`main_clkout0`, 周期 20 ns)

---

## 1. 結論

ビットストリーム `digilent_arty.bit` は生成された。配線は完走しており
(routable net 69719 本すべて完全配線、配線エラー 0)、DRC も Critical なし、
ホールドも余裕がある (WHS +0.034 ns、違反 0)。

しかし **セットアップが大きく落ちている**。

| 項目 | 値 |
|---|---|
| WNS | **-20.442 ns** (要求 20 ns に対し実パス 40.44 ns) |
| TNS | -262585.312 ns |
| 違反エンドポイント | **17702 / 67415 (26%)** |
| 実力周波数 | **約 24.7 MHz** |

このままでは 50 MHz では動かない。以下、原因を段階的に切り分けた。

---

| Slice LUT | 56.16 % | **75.37 %** (47786) | +19 pt |
| Slice (占有) | — | **97.02 %** (15378/15850) | ほぼ満杯 |

## 3. 原因の切り分け — 混雑ではなく「段数」

決定的な証拠は **合成直後 (配置前) のタイミング** にある。

| 段階 | WNS | 違反エンドポイント |
|---|---|---|
| 合成後 (`_timing_synth.rpt`) | **-16.276 ns** | 13635 |
| 配置配線後 (`_timing.rpt`) | -20.442 ns | 17702 |

配置前からすでに -16.3 ns ある。配置配線が追加したのは 4.2 ns にすぎない。
つまり **97 % の混雑は二次的な悪化要因であって、本質は論理段数が深すぎること**。
面積だけ削っても 50 MHz には届かない。

---

## 4. 最悪パスは 2 本

### (A) FPU の 1 サイクル演算 — 合成後の最悪パス

```
wb_rd_reg[0]  →  u_fpu/result_reg[54]
  36.113 ns  (logic 15.596 ns / route 20.517 ns)
  90 段  (CARRY4=59, LUT6=18, ...)
```

`CORE_FPU.sv` の `S_IDLE` が、乗除算以外のすべての演算で
`result <= res_comb` を直接実行している。`res_comb` は

  オペランド入力 → アンパック/特殊値判定 → `shr_jam` 桁合わせ
  → 128 bit 加算 → `lzc129` 先行 0 検出 → 129 bit 可変シフト正規化
  → `FPU_ROUND` (サブノーマルシフト + 丸め + 桁上げ)

を**全部 1 サイクルで**通す。しかもその入口はレジスタではなく
WB からのフォワーディング mux である。論理だけで 15.6 ns、
20 ns 周期の 78 % を使い切っている。配線が 0 でも間に合わない。

### (B) EX → DTLB → PMP → D$ — 配置配線後の最悪パス

```
g_core.u_cpu_core/ex_rs1_reg[4]  →  u_cpu_cache/u_dcache/rob_data_reg[0][18]/CE
  40.257 ns  (logic 10.369 ns / route 29.888 ns)
  52 段  (CARRY4=23, LUT6=18, ...)
```

配置配線後のワースト 10 本のうち **9 本がこの形**で、すべて
`ex_rs1_reg[4]` 始点。経路は

  EX レジスタ → `u_exu` のアドレス加算 (`ex_a_fwd1` はファンアウト 103)
  → `u_mmu/u_dtlb` の `vpn_match`/`hit` → `u_pmp_d/match_one`
  → `d_pmp_fail` → 例外要因合成 → D$ の ROB 書き込みイネーブル

設計時に想定したとおりの
**「アドレス加算 → TLB 引き → PMP 判定 → キャッシュ制御」1 サイクル連鎖**。
論理 10.4 ns、配線 29.9 ns。論理だけなら 50 MHz にぎりぎり載るが、
97 % 混雑下の配線がそれを潰している。

---

## 5. 対策案

| # | 内容 | 期待効果 | 規模 |
|---|---|---|---|
| 1 | FPU: `S_IDLE` から直接 `result` を書かない。オペランドをレジスタに取る `S_OP` を追加し、さらに `rnd_sig/rnd_exp` をレジスタ化して `FPU_ROUND` を次サイクルに送る (FP 演算 +1〜2 サイクル) | (A) を約 1/3 に | 小〜中 |
| 2 | BTB 64 → 16 エントリ | -2600 LUT / -6000 FF、64 way 比較器の段数も減る | 極小 (パラメータ) |
| 3 | I/D TLB 16 → 8、PMP 16 → 8 (DTS も追随) | -3000 LUT 程度、(B) の TLB/PMP 段も短縮 | 小 (パラメータ + DTS) |
| 4 | D 側アドレス変換を MA へ送る (EX はアドレス加算まで、TLB+PMP+キャッシュ要求は次段) | (B) を根本解決 | 大 (パイプライン再構成) |
| 5 | `--sys-clk-freq` を下げる | 即効だが、Arty の LiteDRAM は sys4x = 4×sys のため 25 MHz にすると DDR3 が 200 MT/s となり規格下限を割る。CPU だけ別ドメインにするなら CDC が必要 | 中〜大 |

### 推奨する順序

1. **案 2 + 案 3** を先に入れる(パラメータ変更のみ)。Slice 占有率を
   97 % から 80 % 台に落とし、配線遅延の暴走を止める。
   SIM_CORE / SIM_SYS の回帰で機能に影響がないことを確認する。
2. **案 1** で FPU を分割する。合成後 WNS がどこまで戻るかを測る。
3. 残るのが (B) だけになった段階で、案 4 が必要かを判断する。
   論理 10.4 ns なので、混雑が解けた後の配線次第では案 4 なしで
   50 MHz に載る可能性がある。

各ステップごとに合成だけ回して `_timing_synth.rpt` の WNS を見れば、
配置配線を待たずに効き目が判定できる。

## 6. 第 1 段の実施内容 (2026-09-23)

### 入れた変更

| 対象 | 変更 | 狙い |
|---|---|---|
| `CORE_BTB` | 64 エントリのまま**分散 RAM 化**。valid のみフロップ | 面積(3474 LUT + 8000 FF → 数百 LUT + 64 FF の見込み)。予測性能は不変 |
| `MMU_TLB` | 16 → **8 エントリ**、引き当てを 1-hot 選択に | 面積 + パス (B) の段数 |
| `MMU_PMP` | 16 → **8 エントリ**、1-hot 選択、NAPOT マスクを辺で共有、冗長な `hit_lo != hit_hi` を削除 | 面積 + パス (B) の段数 |
| `CORE_CSR` | `PMP_CSRS = 16` を新設。判定は 8 本、CSR は 16 本見せてゼロを読む | 特権仕様(0/16/64 エントリ)への適合 |
| `mmrisc_arty.dts` | `d/i-tlb-size` 8、`riscv,pmpregions` 8 | 実装との一致 |

**BTB は縮めなかった**。当初案は 64 → 16 だったが、直接写像で書き込み 1 本・
読み出し 2 本という形はファブリックの分散 RAM にそのまま載る。縮めるより
削減幅が大きく、しかも予測の届く範囲を落とさない。

### 検証

| 項目 | 結果 |
|---|---|
| SIM_CORE (17 本) | PASS |
| SIM_SYS (12 本) | PASS |
| Icarus (4 値) | PASS ―― 未初期化 RAM の X はどこにも漏れない |
| riscv-tests | 132 passed / 既知の失敗のみ |
| SIM_MMU PMP バグ注入 | **19 検出 / 0 見逃し / 0 未適用** |
| Verilator lint | 警告 57 → 56 |

サイクル数は t14_mmu の +9(14159 → 14168、TLB 8 本化による walk 増)を除いて
**全本数で完全に一致**。とくに t17_btb 931、t16_bench 33556 が 1 サイクルも
動いていないことが、BTB の RAM 化が予測判断を 1 つも変えていない証拠になる
(予測器は透過なので、挙動の違いは答えではなくサイクル数に出る)。

バグ注入で 1 件の**設計上の発見**があった。PMP を 1-hot 化すると
`sel_lo != sel_hi` が「片端だけ一致」の場合も含むようになり、
`hit_lo != hit_hi` の行が死ぬ。それを突いていたミューテーションが検出されなく
なったことで気づき、行を削って別の形のミューテーションに差し替えた。

### 次にすること

Vivado で**合成だけ**回し、`_timing_synth.rpt` の WNS と
`_utilization_synth.rpt` の LUT / Slice を見る。判断の目安:

- Slice 占有が 80 % 台に落ちているか(配線遅延の暴走が止まるか)
- 合成後 WNS が -16.3 ns からどこまで戻ったか
  ―― パス (A) の FPU には手を付けていないので、**大きくは戻らない見込み**。
  パス (B)(EX → DTLB → PMP → D$)の論理段数がどれだけ減ったかを、
  ワーストパスの `Logic Levels` で見るのが本命。

その結果を見てから第 2 段(FPU の分割)に進む。

## 7. 第 1 段の合成結果 (2026-09-23)

配線はまだ途中(`digilent_arty_timing.rpt` は前回のまま)。合成と配置が
終わっているので、**同じ工程どうし**で比較する。

### 面積 ― 混雑は解けた

配置後 (place 対 place):

| 項目 | 第 1 段前 | 第 1 段後 | Rocket |
|---|---|---|---|
| Slice LUT | 47786 (75.37 %) | **40016 (63.12 %)** | 56.16 % |
| **Slice 占有** | **97.02 %** | **73.61 %** | ― |
| Slice Register | 30573 (24.11 %) | **20695 (16.32 %)** | ― |
| 分散 RAM (LUT) | 302 | 549 | ― |
| Block RAM | 44 (32.59 %) | 44 (32.59 %) | 26.30 % |
| DSP | 32 (13.33 %) | 32 (13.33 %) | 6.25 % |

**Slice 占有 97 % → 73.6 %**。配置器が身動きできる水準に戻った。
これが第 1 段の主目的だった。

### 階層別 (配置後)

| 階層 | 前 LUT / FF | 後 LUT / FF |
|---|---|---|
| `u_btb` | 3474 / 8000 | **414 (論理 167 + RAM 247) / 64** |
| `u_csr` | 6585 / 1786 | 3317 / 1306 |
| `u_mmu` | 6484 / 3315 | 5034 / 1785 |
| 　`u_dtlb` | 2198 / 1556 | 1125 / 779 |
| 　`u_itlb` | 2675 / 1508 | 1081 / 755 |
| 　`u_pmp_d` / `u_pmp_i` | (`u_csr` に吸収されて見えず) | 1018 / 985 |
| 　`u_ptw` | 1063 / 130 | 428 / 130 |
| `u_lsu` | 9301 / 32 | 8173 / 32 |
| `u_fpu` | 3008 / 952 | 4294 / 952 |
| `u_dcache` | 6501 / 4274 | 6611 / 4309 |

BTB は**予測どおり 1 桁小さくなった**(-3060 LUT、-7936 FF)。フリップフロップの
総減少 9878 本は、BTB 7936 + TLB 1530 + PMP レジスタ 480 の見積もり 9946 と
1 % 以内で一致する。

`u_fpu` が増えて `u_lsu` が減っているのは中身が動いたわけではなく、
**越境最適化の帰属が戻った**だけである(両者の和は 12309 → 12467 でほぼ不変)。
前回 126 行の `CORE_LSU` に 9301 LUT が付いていたのがそもそも FPU 出力段の
吸収だった、という読みの裏が取れた形になる。

### タイミング ― TNS は 1/3、WNS は据え置き

合成後 (synth 対 synth):

| 項目 | 第 1 段前 | 第 1 段後 |
|---|---|---|
| WNS | -16.276 ns | **-16.439 ns** |
| TNS | -121911 ns | **-39779 ns**(-67 %) |
| 違反エンドポイント | 13635 / 90725 (15.0 %) | **5821 / 63111 (9.2 %)** |
| 違反 1 本あたりの平均 | -8.94 ns | **-6.83 ns** |

**WNS が動かないのは予定どおり**。手を付けていないパス (A)(FPU)が
そのまま最悪パスに残っている:

```
CPU_TOP/g_core.u_cpu_core/ma_rd_reg[3]  →  u_fpu/result_reg[54]
  36.276 ns  (logic 15.237 ns / route 21.039 ns)
  86 段  (CARRY4=56, LUT6=18, ...)
```

前回の 36.113 ns / 90 段とほぼ同一で、始点が `wb_rd` から `ma_rd` に
変わっただけ。**論理だけで 15.2 ns** という壁は動いていない。

一方 **TNS が 1/3、違反本数が 43 % に減った**のは、TLB と PMP の優先度チェーンを
1-hot にした効果が全体に効いているということ。パス (B) 系統が大量に
違反リストから抜けたと見てよい。

### この時点の判断

- 第 1 段の目的(混雑の解消)は**達成**。
- 50 MHz を塞いでいるのは**ほぼ FPU 単独**になった。
- パス (B)(EX → DTLB → PMP → D$)の新しい段数は、配線が終わった
  `digilent_arty_timing.rpt` で確認する。合成後の最悪パスに顔を出さなく
  なったので、52 段からは確実に減っている。

次は第 2 段(FPU の分割)。論理 15.2 ns を 3 分割できれば 1 段あたり 5 ns 強、
73 % 占有での配線を足しても 20 ns に収まる見込みが立つ。

## 8. 第 1 段の配置配線結果

| 項目 | 第 1 段前 | 第 1 段後 |
|---|---|---|
| WNS | -20.442 ns | **-16.786 ns** |
| TNS | -262585 ns | **-81165 ns**(-69 %) |
| 違反エンドポイント | 17702 / 90675 (19.5 %) | **7903 / 63179 (12.5 %)** |
| **配線が足した遅延**(synth → route) | +4.17 ns | **+0.35 ns** |
| 実力周波数 | 24.7 MHz | **27.2 MHz** |
| Slice 占有 | 97.02 % | 73.61 % |

配線は完走(56084 本すべて)、配線エラー 0、DRC は Critical なし、
ホールド +0.053 ns で違反 0、消費電力 0.826 W。

配線が足した遅延が **4.17 ns → 0.35 ns** に落ちたのが、混雑が解けたことの
直接の証拠である。

そして**ワースト 10 本がすべて FPU で終わっている**。パス (B)
(EX → DTLB → PMP → D$)は上位から消えた。

FPU には長いパスが**2 本**あることも分かった。

```
ma_rd_reg[3] → u_fpu/result_reg[*]   36.7 ns  97 段 CARRY4=74  logic 17.0 ns
wb_rd_reg[0] → u_fpu/sum_r_reg[*]    36.7 ns  89 段 CARRY4=62  logic 14.1 ns
```

後者は `S_M2`(桁合わせ `shr_jam` → 129 bit 比較 → 加減算)、
前者は `S_A3` / `S_IDLE` の `res_comb`(先行 0 検出 → 129 bit 正規化シフト
→ 選択 → 丸め)。

## 9. 第 2 段の実施内容 (2026-09-23)

### 入れた変更(`CORE_FPU.sv`)

| # | 変更 | 狙い |
|---|---|---|
| 1 | オペランドを `start` のサイクルに**ユニット自身のフリップフロップへ写す**。最初の 1 サイクルだけ生の値をバイパス | フォワーディング多重化器と展開(前置 0 検出 + バレルシフト)を全経路の先頭から外す |
| 2 | `S_A3` を **`S_SEL`(答えの組み立て)と `S_RND`(丸め)** に分割。丸め器の入力をレジスタ化 | 17.0 ns の論理を 2 分割 |
| 3 | `S_M2` を **`S_M2`(桁合わせ)と `S_M3`(加減算)** に分割 | 14.1 ns の論理を 2 分割 |
| 4 | `S_M3` は「加算」「差」「逆向きの差」を**並べて作って選ぶ**。比較→減算の直列をやめる | 129 bit の桁上げ鎖を 2 本直列から 1 本に |

### サイクルコスト

| 演算 | 前 | 後 |
|---|---|---|
| 比較 / FCLASS / 符号操作 / FMV / FCVT | 2 | **4** |
| FADD / FSUB / FMUL / FMA | 5 | **7** |
| FDIV / FSQRT | N+3 | **N+4** |

`t11_fp` が 1390 → 1553 サイクル(+11.7 %)。**それ以外は 1 サイクルも動かない**
(`t16_bench` 33556 のまま ―― このベンチは FP を使わない)。

### 検証

| 項目 | 結果 |
|---|---|
| SoftFloat 比較(既定) | PASS 450240 checks ―― 変更前と同数 |
| SoftFloat 比較(`+rand=20000`) | **PASS 4935240 checks** |
| SIM_CORE / SIM_SYS | PASS |
| riscv-tests | 132 passed / 既知の失敗のみ |
| **SIM_FPU バグ注入(新設)** | **17 検出 / 0 見逃し / 0 未適用** |

`SIM_FPU/bug_inject.sh` は今回新しく作った。**ある状態で書いて別の状態で読む
レジスタ**は、間違った所につないでも lint に掛からず波形でも気づきにくいので、
分割で生まれたその切れ目を 1 つずつ壊して、SoftFloat 比較が落ちることを
確かめている。

### 次にすること

Vivado を回して確認する:

- 合成後 WNS が **-16.4 ns からどこまで戻ったか**。FPU の論理 17.0 ns / 14.1 ns
  をそれぞれ 2 分割したので、8 ns 前後まで落ちていれば狙いどおり。
- 新しいワーストパスが**どこになったか**。FPU が退けば、次はパス (B)
  (EX → DTLB → PMP → D$)が戻ってくるはずで、その論理段数が第 1 段で
  どこまで減ったかがここで初めて見える。

RTL は `digilent_arty.tcl` から相対パスで参照されているので、**LiteX の
再生成は不要**、Vivado をそのまま回せばよい。

なお第 1 段で DTS を変えている(TLB 8、PMP 8)ので、**Linux を起動する前に
`mmrisc_arty.dtb` を作り直す**必要がある(`docs/BRINGUP.md` 参照)。

## 10. 第 2 段の合成結果 ―― 悪化した (2026-09-23)

| 項目 | 第 1 段後 | 第 2 段後 |
|---|---|---|
| 合成後 WNS | -16.439 ns | **-26.021 ns** |
| 配置配線後 WNS | -16.786 ns | **-28.141 ns** |
| 配置配線後 TNS | -81165 ns | -126869 ns |
| Slice 占有 | 73.61 % | 79.02 % |
| Slice LUT | 40016 | 39804 |

配線・DRC・ホールドはすべてクリーン。面積もほぼ横ばい。**合成の時点で
すでに悪化している**ので、これは配置配線ではなく設計の問題である。

### 原因 1 ―― 切る場所を間違えていた

第 2 段は末尾を「答えの組み立て」と「丸め」に割った。しかし `sp_res`
(丸めを通らない答え)は**定義上、丸め器を読まない** ―― RTL のコメントが
「丸め器の出力を読むと組み合わせループになる」と警告しているとおりである。
つまり**丸め器はもともとその経路に乗っていなかった**。

長いのは組み立ての側だけで、その先頭にあるのが**展開**(サブノーマルの
前置 0 検出 64 ビット + 全幅シフト)だった。a/b/c をレジスタ化したことで
フォワーディング多重化器は先頭から外れたが、展開と選択は 1 サイクルに
残ったままだった。

```
第 2 段後の合成ワースト:
  ex_rs1_reg[4] → u_fpu/q_sp_res_reg[32]   96 段 / 論理 17.6 ns
第 1 段後の合成ワースト(比較):
  wb_rd_reg[0]  → u_fpu/result_reg[54]     90 段 / 論理 15.6 ns
```

段数がほぼ同じ。**割ったつもりで割れていなかった**。

### 原因 2 ―― バイパス多重化器

`u_a = start ? a : q_a` を置いたのが二重に効いた。

1. **`start` は早い信号ではない**。パイプラインはメモリ段がストールして
   いないときにしか上げず、それは D$ の応答で決まる。その信号が
   ユニット最深コーンの先頭にある多重化器の選択に来た。配置配線後の
   ワーストパスが `u_lsu/size_r_reg → lsu_resp_data → q_a → …` と
   **D$ の応答から始まっていた**のがこれである。
2. **タイミング解析は状態機械の状態を知らない**。`start` のサイクル
   (S_IDLE)に生のオペランドから、何状態も先の `S_SEL` でしか書かれない
   `q_sp_res` まで届く経路を、実在するものとして解析していた。

### 入れ直した内容

| # | 変更 |
|---|---|
| 1 | **バイパスを廃止**。`S_IDLE` はオペランドと制御(`op`/`fmt`/`rm`/`int_*`)の写しを取るだけにし、`start` のサイクルにやっていたことは新設の `S_UNP` へ移した |
| 2 | **展開を割る**。「どんな値か」(符号・0・∞・NaN・signalling)は比較数個なので組み合わせのまま、**指数と仮数だけを `S_UNP` で保持**。以降のすべてのコーンから前置 0 検出と全幅シフトが外れる |
| 3 | **部分積を `S_PP` に分離**。展開 → DSP 乗算が 1 サイクルに同居しないように |
| 4 | 丸め(`S_RND`)と桁合わせ/加減算(`M2`/`M3`)の分割は**そのまま残す**。129 ビットの先行 0 検出 + 正規化シフトに丸めを足すとやはり入らないため |

### サイクルコスト

| 演算 | 元 | 第 2 段 | 入れ直し後 |
|---|---|---|---|
| 比較 / FCLASS / 符号操作 / FMV / FCVT | 2 | 4 | **5** |
| FADD / FSUB / FMUL / FMA | 5 | 7 | **9** |
| FDIV / FSQRT | N+3 | N+4 | **N+5** |

`t11_fp` 1390 → **1655** サイクル(+19 %)。**それ以外は 1 サイクルも動かない**
(`t16_bench` 33556 のまま)。

### 検証

| 項目 | 結果 |
|---|---|
| SoftFloat 比較(`+rand=20000`) | **PASS 4935240 checks** |
| SIM_CORE / SIM_SYS | PASS |
| riscv-tests | 132 passed / 既知の失敗のみ |
| SIM_FPU バグ注入 | **20 検出 / 0 見逃し / 0 未適用**(新しいレジスタ向けに 3 本追加) |

### 学んだこと

**「段を割った」は合成で確かめるまで信じない。**割ったつもりの seam に
そもそも遅延が乗っていないことがある。今回は RTL のコメント自身が
「丸め器は `sp_res` の経路に乗らない」と書いていたのに、それを読み落として
そこを割った。

**状態機械を持つユニットにバイパスを置くときは、タイミング解析が状態を
知らないことを思い出す。**実在しない経路を作り、しかもそれが最悪パスになる。

### ワーストパスの区間内訳(実配線)

ワースト 10 本はすべて同じ系統 `ma_rd_reg[1] → u_ifu/pq_*`。
論理 9.47 ns に対し**配線 24.5 ns (72 %)**。

| 区間 | 遅延 | 中身 |
|---|---|---|
| 転送多重化 | **5.46 ns** | `ma_rd` → 一致比較 → `ex_a_fwd`(うち配線 4.5 ns、fo=197 の網を含む) |

転送多重化に 5.46 ns、PMP に 10.27 ns というのは削り代が残っている数字である。

### 選択肢

#### 案 1 ― 細かく削る(サイクル数そのまま、性能コストゼロ)

| | 内容 | 期待 |
|---|---|---|
| 1a | **転送一致の先行計算**。`ma_rd == ex_rs1` の比較を ID 段で済ませ、EX には一致ビットだけ渡す。5.46 ns のうち比較と長い配線が消え、多重化器だけになる | 2〜3 ns |
| 1b | **PMP の `last_byte`**。`paddr + size` → `paddr \| mask`。アクセスは必ず自然整列(不整列は MMU に届く前にトラップ、命令面は 8 バイト整列、PTW も 8 バイト整列)なので桁上げは起きえない。54 bit 桁上げ鎖が 1 本消える | 2〜3 ns |
| 1c | **PMP の TOR 比較**を `a >= prev && a < this` の 2 本から 1 本の減算 + 借りにまとめる | 1〜2 ns |

合計 5〜8 ns → 26〜29 ns。**50 MHz には届かないが 35 MHz には届く。**

1b は tb_PMP が不整列アドレスも生成するので、「整列前提」をパラメータで
明示し、ベンチ側もそれに合わせる必要がある(`MMU_PMP` の一般性は落ちる)。

#### 案 2 ― リダイレクトをレジスタ化(IFU が 1 サイクル遅れて反応)

末尾の 6.00 ns(fo=1127 の flush 網 → パーセルキュー全体)が切れる。
**代償は予測ミス・トラップ・fence のたびに +1 サイクル**(予測ミスペナルティ
3 → 4)。`t16_bench` と `t14_mmu` で実測できる。

案 1 と合わせて 11〜14 ns → 20〜23 ns。**50 MHz にぎりぎり届くかどうか。**

#### 案 3 ― PMP を独立段へ(パイプライン +1 段)

前半(転送 + 加算 + TLB)14.8 ns / 後半(PMP + 例外 + キャッシュ要求)19.2 ns。
両方 20 ns に入るが後半がぎりぎりなので案 1 との併用が前提。
**代償はロードユースのバブルが 2 → 3。**ストアは追加コストなし、
リプレイ機構は不要、キャッシュには手を入れない。

なお仕様書 3 章の第 1 案「TLB を独立段に」**だけでは足りない** ―― 後半が
TLB + PMP + 末尾で 22.8 ns 残る。切るなら **PMP の手前**である。

#### 案 4 ― 並列 VIPT(仕様書の第 2 案、サイクル数そのまま)

キャッシュは既に `req_paddr` を「受理の次のサイクル」に受ける設計
(`CPU_CACHE_SPEC.md` 5.6 / 7b)なので、索引は EX で出し物理タグは次サイクルに
届く。**サイクルコストなし**だが、キャッシュに kill 入力を足し、TLB ミス時の
リプレイ機構が要る。検証済みのキャッシュに手を入れるのが最大のリスクで、
作業量は 4 案中最大。

#### 案 5 ― クロックを下げる(**推奨しない**)

30 MHz なら今のビットストリームで既に動く(あと 0.75 ns)。だが **LiteDRAM は
sys4x = 4×sys に構造的に固定**されている ―― PLL は VCO 1600 MHz、
CLKOUT0 /32 = 50 MHz(sys)、CLKOUT2/3 /8 = 200 MHz(sys4x / sys4x_dqs)、
CLKOUT4 /8 = 200 MHz(idelay、IDELAYCTRL が要求する固定値)。
sys を下げると DDR3 のクロックも比例して下がり、現状 200 MHz(DDR3-400)で
既に JEDEC 下限 303 MHz を割っているところを、30 MHz にすると 120 MHz まで
落ちる。DLL がロックしない可能性が高い。

CPU だけ別ドメインにして SoC/DRAM を 50 MHz のまま残す手はあるが、バスの
CDC を自作することになり案 3 や案 4 より重い。

### 決めたこと

**案 1 を全部やってから再合成し、その数字で案 2 / 案 3 を決める。**

1. 案 1 は性能コストがゼロで、5〜8 ns という大きさは「段を増やすか」の判断
   そのものを変えうる。
2. この経路は一度も最適化されていないので、削り代が残っている。
3. 測ってから段を増やす順序は、予測器やロードユースのとき(決定 36、37)と
   同じこのプロジェクトの流儀に合う。

案 1 で 35 MHz に載るなら、**そこで一度 Linux を通してしまう**選択肢も
現実的になる(DDR3 は 140 MHz。これも要実験だが 30 MHz よりは可能性がある)。
起動が取れれば以降の最適化は実測ベースで進められる。

## 12. 案 1 の実施 (2026-09-23)

11 章で決めたとおり、サイクル数を変えない 3 項目を入れた。**再合成待ち**。

### 1a ― 転送元の選択を 1 サイクル前に決める(`CPU_CORE.sv`)

`ex_a_fwd` / `ex_b_fwd` の多重化器の選択を、`ma_rd == ex_rs1` などの比較から
フリップフロップ 4 個(`fwd_a_ma / fwd_a_wb / fwd_b_ma / fwd_b_wb`)に置き換えた。
次のサイクルに EX・MA・WB が持つ命令は、パイプラインレジスタを動かすのと同じ
信号で決まるので、比較はそれに対して前もって済ませ、答えだけ保存する。
経路の先頭は「フリップフロップ → 64 bit 多重化器」になり、`ma_rd` の配線と
5 bit 比較が消える。

入力側(フリップフロップの D)には `ex_advance` と `ex_exc` が入るが、どちらも
既に EX/MA のパイプラインレジスタのイネーブルと D に入っている信号で、
新しく長い経路を作るものではない。

### 1b + 1c ― PMP の加算と比較(`MMU_PMP.sv`)

検査対象を「`paddr` を含む 2^size バイトの自然整列ブロック」と定義し直した。
その両端はワードアドレスのビット 0 しか違わないので:

- `last_byte = paddr + size` の 64 bit 加算が消えた(ビット 0 を立てるだけ)
- ビット 53:1 の `<` と `==` をエントリごとに 1 本だけ作り、両端で共有
- TOR の下限は一つ前のエントリの上限比較の否定を使う

比較器はエントリあたり 4 本から 2 本、8 エントリで 32 本 → 16 本。
アドレスの各ビットが駆動する先も半分になるので、配線 72 % の経路には
段数以上に効くはず。

**11 章の前提の訂正**: 「命令面は 8 バイト整列」は誤りだった。BTB の予測先に
飛んだ直後は `fetch_pc = btb_target` で、8 バイトの途中を指す。旧 RTL はそこから
`+7` まで検査していたので、実行可能領域の末尾近くに予測で飛ぶと**次の 8 バイト**
まで見て誤って拒否しえた(潜在バグ。Linux では領域が大きく整列しているので
まず表に出ない)。新しい定義では取ってくる 8 バイトそのものを検査するので、
これも同時に直る。パラメータで整列前提を切り替える案は、この定義で不要になった。

### 検証

| 項目 | 結果 |
|---|---|
| SIM_MMU `make pmp` / `long` / `iverilog` | PASS(20 万 / 200 万 / 2 万件) |
| SIM_MMU バグ注入 | **21 / 21 検出**(付け替え 9、追加 2) |

1a は導入時に、旧来の比較と新しいフリップフロップを**毎サイクル突き合わせる
検査**を一時的に入れ、上の SIM_CORE・SIM_SYS・riscv-tests の全実行で不一致 0 を
確かめてから外した。検査が効くことは、選択を壊した版で不一致が出ることで確認した。

SIM_CORE の変異は 18 / 19 を新しい形に付け替え、次状態の規則を壊す 4 本
(188 ストール中に次の命令のソースを見る、189 MA で待つロードを忘れる、
190 x0 への書き込みを転送する、192 MA の命令の有無を見ない)を足した。
「WB からの選択が MA のストールを見ない」は、ストール中の MA は命令を持ち続け
MA 側の選択が必ず立って優先されるので**原理的に検出できない**。ヘッダに理由を
書いて外した。

M174(以前から NOT DETECTED の BTB 変異)は今回**検出**された。原因は RTL では
なく、キャンペーンが走らせる仮想記憶の試験 `rv64ui-v-add` の hex が
`make riscv-tests-v` を走らせたことで存在していたこと。その試験を外すと
M174 は再び未検出になることを確かめた。ヘッダにこの条件を書いた。

### 検証環境で見つけたこと ― Verilator が `$urandom` の if を併合する

tb_PMP に不整列アドレスを混ぜたところ、**旧 RTL でも PASS** した。調べると、
不整列にするケースがすべて上位ビット反転のケースと重なり、どの領域からも
遠いアドレスになっていた。原因は **Verilator 5.020 が、条件の字面が同じ
`if` を 2 つ続けて書くと 1 つに併合する**こと(`$urandom()` の副作用を
無視する)。`if ($urandom() % 8 == 0)` を 2 行続けたので、2 回目の抽選は
行われず、1 回目と同じ答えになっていた。小さな再現で `x & y` が `x` と
完全に一致することを確かめた(独立なら 1/8)。

抽選を先に変数へ取ってから `if` で使う形に直し、旧 RTL で不一致が出る
(ベンチが効く)ことを確かめた。SIM 以下の全ベンチを走査し、字面が同じ
`$urandom` の `if` が近くに並ぶ箇所は**他にない**ことも確認した。

## 14. A(リダイレクトの切り離し)と C(丸め器の 2 段化)、ロードの多いベンチ (2026-09-23)

13 章の「おすすめの進め方」どおり、サイクルコストのない A と、FP だけに効く C を
入れ、B(案 3)のコストを測るベンチを作った。**再合成待ち**。

### A ― 予測の外れの直し方を 2 通りに分けた(`CPU_CORE.sv`、決定 46)

- **制御転送**(分岐・JAL・JALR)の外れは今までどおり EX から直すが、条件を
  `ex_advance` → `~stall_ma`、`ex_exc` → `ex_exc_pre` にした。制御転送は MMU も
  MDU/FPU も使わないので、その命令にとってこの置き換えは**厳密に同じ**
  (`mdu_active` / `fpu_active` は EX がその命令を持つときしか立たない)。
  BTB の更新条件も同じ形にした(書き込みイネーブルも長い経路に乗っていた)。
- **制御転送でない命令が成立と予測された**場合は、EX で直すのをやめ、MA で
  コミットするときに直後から取り直す(`fence.i` / `SFENCE.VMA` と同じ道、
  `refetch_taken`)。これが起きるのは ASID の切り替えで同じ仮想アドレスに別の
  コードが見えるときで、その命令はロードかもしれない。EX で直すとメモリ経路が
  またリダイレクトに乗る。1 サイクル遅くなるのはこの場合だけ。

これで**リダイレクト → IFU → I$ の 4.28 ns が最悪経路から外れる**はず。終点は
`ex_advance` の網(EX/MA の全レジスタのイネーブル、fo=1144)になり、見積もりは
WNS ≈ -6 ns。

既存の 17 本はどれも「制御転送でない命令の外れ」を一度も起こさない(全試験で
取り直しの回数を数えて 0)。そこで **`t18_asid`** を足した: 二つのページテーブルで
同じ仮想ページを別の物理ページに写し、ASID 1 で分岐を BTB に覚えさせてから
フェンスなしで ASID 2 に切り替えると、同じ場所に加算・ロード・除算がある。
取り直しを止めた RTL で落ちることを確かめた。最初の版は BTB のインデックス
(ビット 8:3)の衝突で 1 件目が予測されておらず、取り直しが 4 回起きることを
数えて気づいた。

### C ― 丸め器を 2 サイクルに(`FPU_ROUND.sv` / `CORE_FPU.sv`、決定 47)

2 サイクル目: +1(53 ビット)と詰め込み。桁上がりは「残すビットがすべて 1 で
切り上げる」ときと足す前にわかるので、指数フィールドとオーバーフロー判定は
両方の場合を 1 サイクル目で作り、2 サイクル目は選ぶだけ。tininess 判定の
無制限精度の桁上がりも同じ形で加算器が消えた。128 ビット幅だった +1 は 53 ビットに。

FP 演算 1 命令あたり +1 サイクル(`t11_fp` 1655 → 1739、SIM_SYS 1683 → 1762)。

17 章で直した二系統(D$ の AMO、MR → 要求)は上位から消えた。代わりに、
**それまで隠れていた命令面の系統**が出た。配置が変わって配線が伸びた分、WNS は
前回より悪い数字になっている。

### ワーストパス(実配線 20.79 ns、配線 75 %)

`u_ifu/fetch_pc` → ITLB(vpn 一致 → sel → ppn / level、8.1 ns)→ 命令面の PMP
(比較の CARRY4 鎖 + 後半、8.6 ns)→ フォールト → IFU の「キャッシュに出すか、
自分で応答するか」→ パーセルキューへの書き込み(4.0 ns)。

データ面が MR 段の前に持っていたのと同じ形 ―― **変換と PMP が同じサイクル**。
アドレスがレジスタ(`fetch_pc`)から出る分だけ短く、今まで表に出なかった。

### 直したこと ―― 命令面の PMP を 1 サイクル後に(サイクルコストは実質なし)

- IF1 は変換のフォールトだけを見る(ITLB のページフォールト、ウォークが残した
  アクセスフォールト)。
- PMP は、IFU がキャッシュに渡すために保持している物理アドレス `i_req_paddr` に
  かける。これはキャッシュがステージ 1 でタグを比べるサイクルと同じで、キャッシュは
  **まだ配列の応答もバスへのアクセスも始めていない**。
- 拒否なら、新しい端子 **`i_cancel`** でステージ 1 の要求だけを取り消す(I$ は
  `i_kill` と同じ扱い。SIM_CORE のメモリモデルは、その要求だけを応答の列から外す)。
  そのサイクルは新しい要求を出さない。
- 取り消した要求は IFU の記録に残り(`pr_cancel`)、先頭に来たところで IFU が
  アクセスフォールトのパーセルを積む。応答の順序はそのまま。

コストは PMP に拒否されたフェッチの応答が 1 サイクル遅れることだけ
(`t13_pmp` +2)。他のサイクル数は変わらない。

経路の見積もり: IF1 は ITLB 8.1 + フォールト + IFU 4.0 ≒ 14 ns、IF2 は
`i_req_paddr` → PMP 8.6 → 取り消し → I$ / IFU ≒ 13 ns。

### 検証で見つけたこと

変異「拒否の判定を、直前に出した要求がないサイクルにも使う」が、既存の試験では
検出されなかった。これは本物のバグになる: 古いアドレスで取り消しが続き、新しい
要求が出なくなる。既存の試験の拒否されたフェッチはすべて M にトラップしており、
M は鍵のないエントリに縛られないので、特権が変わった時点で自然に解けていた。
`t13_pmp` に「**S に委譲された**命令アクセスフォールト」を足した。トラップのあとも
S のままなので、同じエントリがかかったまま `stvec` からのフェッチが始まる。
その変異で落ちることを確かめた。

キャッシュ側の二つ(I$ が `i_cancel` を見ない、取り消しのサイクルに新しい要求を

### 余裕はゼロ

0.06 ns 以内の経路はすべて **FPU の答えの組み立て**(`a_exp` → `q_sp_res`、

`S_SEL` の中の変換(整数 ↔ 浮動小数点)を別状態に出す(FP の一部の命令で +1)か、
Vivado の配置配線の努力レベルを上げる(サイクルコストなし、ビルド時間が伸びる)。
まずは実機で動かし、Linux の起動を優先する。

## 20. 実機: バナーの 16 文字で止まった ―― 割り込みが来なかった (2026-09-24)

タイミング成立版(19 章)を書き込むと、ターミナルには `        __` だけが出た。
これは LiteX のバナーの**先頭**で、CPU は ROM から BIOS を取って C を実行し、
UART に書いていた。

### 原因

- BIOS の UART は割り込み駆動(`UART_INTERRUPT`)。最初の 16 文字は TX FIFO に
  直接入り、それ以降はリングバッファに溜まって、割り込みハンドラが送り出す。
  改行 + `\e[1m` + `        __` + 空白 = ちょうど 16 文字。
- 割り込みが来なかった。**PLIC のソース 1 の優先度が 0 のまま**だった(優先度 0 は
  「決して割り込まない」)。
- D$ は非キャッシュのロード / ストアを **8 バイトに丸めたアドレス**で AXI-Lite に
  出していた。内蔵 PLIC は 32 bit レジスタのどちらの半分かをアドレスのビット 2 で
  決めるので、`0x0C00_0004`(ソース 1 の優先度)への書き込みはビット 2 が 0 になり、
  下半分のストローブを見て落ちた。読み出しも同様で、丸めると claim(+4)の読み出しと
  threshold(+0)の読み出しが区別できない(claim は副作用つき)。

### なぜ今まで見えなかったか

| 環境 | 理由 |
|---|---|
| SIM_CORE(`t15_plic`) | メモリモデルが PLIC にバイト単位のアドレスを渡していた |
| SIM_SYS / SIM_CPU | 外部割り込み線を 0 に固定。PLIC を CPU_TOP 越しに使う試験が無かった |
| `make romboot` | 非キャッシュフェッチだけを見る小さなスタブ |

**実際の BIOS を割り込み込みで走らせたことが一度も無かった。**

### 再現と修正

`SIM/SIM_BIOS` を作った: CPU_TOP + 本物のキャッシュ + 本物の `bios.bin`、周辺側は
ROM / SRAM / ctrl / timer0 と LiteX の UART(`uart.py` どおり 16 段 FIFO、TX イベントは
「満杯でない」のレベル、割り込みは pending & enable)。UART を実機の速さ(1 文字
4340 サイクル)にすると、**実機と同じ 16 文字で止まった**(`prio[1]=0`、トラップ 0)。
UART が速いと FIFO が埋まらず割り込みが要らないので、最初は再現しなかった。

修正は D$ の 2 行: 非キャッシュのアドレスを**バイト単位のまま**出す(`DCACHE.sv`、
`CPU_CACHE_SPEC.md` 5.5)。AXI4-Lite としては合法で、データのレーンは従来どおり
ストローブが示す。LiteX の AXI-Lite → Wishbone 変換は下位 3 bit を捨てるので、
外側の SoC には影響しない。修正後の SIM_BIOS: バナー、SoC 情報、`Initializing SDRAM`
まで進む(その先の DDR の較正はモデル化していないので失敗する)。

`make check`(SIM_BIOS)を回帰試験にした: 1 文字 2000 サイクルの UART で、
`Initializing SDRAM` に届き、かつ UART 割り込みを 1 回以上受けたら PASS
(749 回、298 万サイクル、実時間 5 秒)。丸めたアドレスに戻すと FAIL することを確かめた。

### 検証

| 項目 | 結果 |
|---|---|
| SIM_BIOS `make check` | PASS(修正前は FAIL) |
| SIM_CACHE / SIM_SYS(+ romboot)/ SIM_CPU | PASS |

D$ の変更は非キャッシュ経路のレジスタの入力だけで、タイミングへの影響は無いはず。
ただし 19 章のとおり FPU の `S_SEL` は余裕ゼロなので、再合成で負に振れる可能性はある。
