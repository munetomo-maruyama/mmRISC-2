## 3. 次のテーマ

### E3. TLB に残っているもの

ITLB は 8 エントリ、DTLB は 16 エントリ(E3a、2 章)、完全連想で、アドレスのサイクルで比較する。実機に残っているもの
(`BENCH.md` 26.1): MR が DTLB を待つのは `awk`、`ls`、`tftp` でサイクルの 4.1〜4.2 %、ほかのカーネルの負荷で
2.2〜2.6 %、`gunzip` と `md5sum` で 1 % 未満。ウォーカが ITLB のために動くのは `awk` と `ls` で 2.2〜2.4 %。

| 段 | 規模 | 内容 |
|---|---|---|
| E3b | 小(引数) | **ITLB 16、DTLB 32 エントリ**: シミュレーション(`BENCH.md` 26.2)で `awk` は今から −6.0 %(残りの 88 %)、`gunzip` −0.5 %。実機では `ls` と `tftp` にも 2〜4 % ありそう。引数だけ(`CPU_TOP.sv` の `ITLB_ENTRIES`、`DTLB_ENTRIES`)。合成で見る点: DTLB 自身の経路は今 +0.83 ns 以上(TIMING 45)、スライスは約 93 % に |
| (E3c) | 見送り | L1 TLB とウォーカの間の共有の第 2 レベル 64〜128 エントリ。16 / 32 エントリの後には取れるものがサイクルの 0.5 % 未満しか残らない(26.2)ので、LUT +500〜+1,000 に見合わない |

### W. 書き込み(新規、プロファイルから)

| # | テーマ | 規模 | 内容 | 効くところ |
|---|---|---|---|---|
| W1 | **ライン全体の write-validate** | 中 | コピーはコピー先をラインごとに書くが、いまはどのラインもまず読まれ(write-allocate: L2 ヒットか DRAM の読み出し)、その後すべて上書きされる。MSHR はすでにラインのワードごとにワードとバイトイネーブルを持ち(ストアがそこに合流する、M1)、F2 で MSHR がバスに頼まずに自分でビートを作れるようになった(`ms_zero`)。ラインの先頭ワードへのストアで開いた MSHR は、読み出しの前に数サイクル待つ。合流したストアが 8 ワードすべてを埋めたら、それからビートを作り、読み出しはしない。そうでなければ読み出しはいまより数サイクル遅れて出る。カーネルのコピーのループ(`uaccess.S`、`memcpy`)は、コピー先がそろえば 8 ワードを読んでから続けて書く | ユーザ空間へのコピー(`sdread` の 21 %、`md5sum` の 6.6 %、`tftp` の 3.6 %)、`memcpy`(`forkexec` の 4.2 %)、L2 の読み出し。まずコピーのサンプルがどこに落ちるか(コピー元のロードか、コピー先のストアか: `perf script` のアドレスをホストでカーネルの逆アセンブルと突き合わせる)を確かめる |
| W2 | **キャッシュ無しのストアを待たない(posted)** | 小〜中 | キャッシュ無しの領域(周辺)へのストアは、いまはバスの答え(`b`)を待つ。周辺バスと LiteX のブリッジの往復になる。受けた時点で答え(M1 が `STORE_ACK_LIMIT` より下のキャッシュ可能なストアでするように)、後のキャッシュ無しのロード、AMO、`fence` は出したストアが済むまで待たせる(デバイスが見る順番は変わらない)。出したストアのバスエラーは正確な例外にできなくなる: 割り込みで知らせるか、失敗しうるアドレスへのストアは待たせたままにする。まず `perf script` で、`liteeth_start_xmit` のサンプルが `memcpy_toio`(ストア)にあるのか、LiteEth の状態を見るポーリング(ロード、これでは変わらない)にあるのかを確かめる | `liteeth_start_xmit`(`tftp` の 10.7 %)、SD カードのドライバのレジスタ書き込み |

### E. メモリ階層の残り

### M. メモリ待ちの重ね合わせの残り

### T. タイミング

WNS +0.514 ns。最悪の経路は MR のデータ側 PMP の範囲比較から D$ の早出しリクエストの取り消しへ(`TIMING.md` 45 章):
下の T4(第 2 段)。その後ろに、MA から EX へフォワーディングされるロードの値(44 章)、つまり設計そのものの
ロードから使用までの経路。テーマが余裕を食うまでは何も予定しない。
