# 設計テーマ(最終、2026-10-19 時点: Rev.02)

[English](ROADMAP.md)

**mmRISC-2 は Rev.02 で閉じる。** 伸びが頭打ちになってきた時点(2026-10-17)で決めた基準: 見積もった上限が数 % に
届かないテーマは落とし、残るテーマで得られるのが 1〜2 % になったら閉じる。E3(TLB、ユーザモードの負荷で最大 −20 %)の
あと、測れた狙いのある 2 つのテーマ W1 と W2 を実機で確かめ、W1 は作ってシミュレーションでも測った。どちらも
危険に見合うものは取れない(3 章)。最後に CoreMark を見直して T2 が残したサイクルを失うバグ(決定 82)を見つけ、
最終版で直した。

1 章は Rev.02 の姿、2 章は済んだテーマ(1 行ずつ。経緯はそこに書いた文書にある)、3 章は試して取り込まなかった
テーマとその理由、4 章はこの設計を先へ進める人のための残りのテーマ。この文書の以前の版は git の履歴にある
(Rev.01 のものはタグ `Rev.01`)。

## 3. 試して取り込まなかったテーマ

| # | テーマ | 何をするはずだったか、見積もり | どうなったか | 文書 |
|---|---|---|---|---|
| W1 | **ライン全体の write-validate**(2026-10-18) | コピーはコピー先をラインごとに上書きするが、各ラインはまず読まれていた(write-allocate)。D$ の MSHR が、ストアがミスしたラインの読み込みをストアが続く間は待たせ、ストアが覆ったラインはそれらから作る(`cbo.zero` の道)。命令ごとのプロファイル(`workload.sh ips`)で、コピーのストアが `sdread` のサイクルの約 10 %(1 ラインあたり 170 サイクルのうち 85)待っていたので、見積もりは上限 **`sdread` 6〜8 %、`md5sum` 1.5〜2 %、ほかは 1 % 未満**(現実にはその半分程度) | 作って検証し(SIM_CACHE のセクション 22、掃引、66 種のミューテーション)、SIM_BIOS で遅れのモデル付きで測った: **純粋なコピーで +0.1 %**(3 サイクル待つ版)、8 サイクル待つと悪化(コピー +1.9 %、`__clear_user` +5.0 %)。コピーの間にストアが開いた 33,000 ラインのうち覆われたのは 8 本: ミスしたストアは MA に答えを待たせるので、コピーのストアは 4〜5 サイクルおきにしか来ず、コピー先の読み込み(L2 ヒット)はもともとその陰に隠れていた。85 サイクルはストアそのもののペース(M1b)で、読み込みではない。外した | `BENCH.md` 27・27.1 章 |
| W2 | **キャッシュ無しのストアを待たない(posted)**(2026-10-18) | 周辺へのストアに、`b` ではなくバスが受け取った時点で答え、後のキャッシュ無しのロード・AMO・`fence` はそれを待つ。`liteeth_start_xmit`(`tftp` の約 10 %)がレジスタの書き込みで待っていると考えた | `uclat`(`/dev/mem`)で測った: キャッシュ無しのストアは **13 サイクル**、ドライバの 3 回のレジスタ書き込みと 1 回の読み出しはパケットあたり約 60 サイクルで、その場所のパケットあたり約 3,700 サイクルとは桁が違う。W2 で取れるのは **`tftp` の 0.1 % 未満**、そこのサンプルはこれらのアクセスではない。作らなかった | `BENCH.md` 27 章 |
| (E3c) | 2 段目の TLB(2026-10-17) | 2 つの L1 TLB で共有する 64〜128 エントリ | ITLB 16・DTLB 32 エントリの後には、サイクルの 0.5 % 未満しか残らない。作らなかった | `BENCH.md` 26.2 章 |

W1 が残したものは覚えておく価値がある: コピーのストアが遅いのは、ミスしたストアの答えをコアが毎回待つから。
これは下の M1b で、D$ ではなくパイプライン(副作用のあるストアの順序)の変更になる。

## 4. この先に残すもの

どれも Rev.02 には入っていない。得られるものの大きさでおおよそ並べた。タイミングの余裕(+0.140 ns)とスライス
(残り約 1,130)のため、先に T8 が無いとコアの近くには足せない。

| # | テーマ | 規模 | 内容 |
|---|---|---|---|
| M1b | 受け付けられたストアの答えをコアが待たない | 小〜中 | W1 で分かったこと: ミスしたストアは MA を待たせ、次のストアは MA がコミットするまで出ないので、コピーは 4〜5 サイクルにダブルワード 1 つしか書けない。ユーザ空間へのコピーは `sdread` の 24 % |
| E1b | SD カードの DMA の書き込みを L2 で | 中 | `sdread` / `ext4read` の D$ 待ち(35 % / 26 %)は L2 でも減らなかった。DMA の書き込みは部分書き込みとして L2 を素通りしてメモリへ行く。先にメモリ待ちのイベント(M0)で確かめる |
| M2 | ソフトウェアのプリフェッチ(Zicbop) | 小〜中 | 効くのは自分で書いたコードだけ(行列積: 2.30 → 約 2.0 の見込み) |
| M3b | 需要のミスがプリフェッチを追い越す | 中 | I$ のプリフェッチ(M3、作ったが無効)を有効にするための条件 |
| E1a | L2 の置き換え方式の比較 | 小 | 疑似 LRU とランダム(`SIM/SIM_L2` に掃引がある) |
| E2 | L1 を 16 から 32 KB に | 中 | VIPT のままなら 8 ウェイが要り、ヒットの経路が広がる。たぶん見合わない |
| M4 | ロードのミスで止まらない(使うときに止まる) | 大 | 行列積には効くが、ほかにはあまり効かない |
| T8 | DTLB の権限の検査を 1 サイクル後ろへ | 小〜中 | Rev.02 の最悪の経路は DTLB の比較。one-hot のヒットとフラグを EX の終わりでレジスタに取り、MR で検査する。コアの近くに何か足す前に要る |
| T3 / T4 | `ma_mem` の複製、データ側の PMP の比較を 1 サイクル前へ | 小 | タイミングだけ |
| G2 | トリガの範囲一致 | 小 | gdb の `watch` を変数全体に |
| C1 | ミスアラインのアクセスをハードウェアで | 大 | OpenSBI で 1 回約 1,060 サイクル。Linux は避けている |
| C3 | ASIC(GF180MCU) | 大 | 作業場所は `../mmRISC-2-GF180MCU` |
| C4 | マルチコア | 大 | A7-100T に入らない(スライスの残り約 1,130)。`CPU_CACHE_SPEC.md` 6.4 の手引きはある |
| C5 | FLD と FP 演算を同時に出す | 大 | 実質は新しいパイプライン。FIR 1.50 → 約 1.0 |
