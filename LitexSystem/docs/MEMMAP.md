# Memory map of the mmRISC-2 LiteX system

[日本語](MEMMAP_J.md)

The address map of the system that boots Linux on the Arty A7-100T (`LitexSystem/`), where each region is
implemented (the RTL of this repository, or what LiteX generates), and what runs where during the boot.
Addresses are physical.

## 1. The first instruction after reset

At reset the CPU fetches from **0x1000_0000, the boot ROM of LiteX, which holds the LiteX BIOS**. The ROM is
not a module of `RTL/`: LiteX generates it as block RAM in the SoC, with the BIOS compiled into the bitstream.
The path of that first fetch:

| Step | What | Where |
|---|---|---|
| 1 | The fetch address after reset is the parameter `RESET_VECTOR` of `CPU_TOP`. Its default is 0x8000_0000; LiteX sets it to the address of its ROM, 0x1000_0000 (`set_reset_address`) | `RTL/CPU/CPU_CORE/CORE_IFU/CORE_IFU.sv` (`fetch_pc <= RESET_VECTOR`), `LitexSystem/cpu/mmrisc/core.py` |
| 2 | The address is below `MEM_BASE` (0x8000_0000), so the instruction cache does not cache it: a single 64-bit read goes out on the AXI4-Lite peripheral bus | `RTL/CPU/CPU_CACHE/ICACHE/ICACHE.sv` (`s1_cacheable`), `CPU_CACHE` |
| 3 | The bus arbiters (the debugger's System Bus Access joins here), then `CPU_MMIO`: not the CLINT nor the PLIC, so it goes out of `CPU_TOP` on `m_axil_*` | `RTL/BUS/BUS_ARB/BUS_ARB.sv`, `RTL/CPU/CPU_MMIO/CPU_MMIO.sv`, `RTL/CPU/CPU_TOP/CPU_TOP.sv` |
| 4 | AXI4-Lite to Wishbone, then the SoC bus of LiteX (32-bit Wishbone) and its address decoder | `core.py` (`AXILite2Wishbone`), generated `build/gateware/digilent_arty.v` |
| 5 | The `rom` of LiteX: `Memory rom: 12141-words x 32-bit`, a read-only block RAM initialised from `digilent_arty_rom.init`, which is the BIOS (`build/software/bios/bios.bin`, 48,564 bytes) | `build/gateware/digilent_arty.v`, `digilent_arty_rom.init` |

So the BIOS runs from ROM, uncached, until it hands over to OpenSBI in DRAM (section 6). Because it is generated,
the ROM changes whenever the BIOS is rebuilt (`scripts/build_soc.sh`), and the bitstream with it.

## 2. The one rule of the CPU: `MEM_BASE`

`CPU_TOP` divides the address space at `MEM_BASE` = 0x8000_0000 and at nothing else:

| Addresses | Path | Cached |
|---|---|---|
| ≥ 0x8000_0000 | L1 caches → L2 (`CPU_L2`, 256 KB) → AXI4 memory bus (`m_axi4_*`) → LiteDRAM | Yes (I$, D$, L2) |
| < 0x8000_0000 | AXI4-Lite peripheral bus → `CPU_MMIO` → CLINT / PLIC inside the CPU, everything else out on `m_axil_*` to the SoC bus | No |

Addresses are 40 bits inside `CPU_TOP`; LiteX works in 32, and `core.py` drops the upper 8 bits (every address of
this SoC is below 4 GB). LiteX declares the ROM and the SRAM "cached" only because it refuses to put a ROM in an
IO region; the hardware does not cache them (`core.py`, `io_regions`).

## 3. Physical map

| Address | Size | Region | Implemented by | Bus, cached |
|---|---|---|---|---|
| 0x0200_0000 – 0x0200_FFFF | 64 KB | **CLINT** (software interrupt, timer) | `RTL/CPU/CPU_CLINT` inside `CPU_TOP` | Peripheral, no |
| 0x0C00_0000 – 0x0C3F_FFFF | 4 MB | **PLIC** (the device tree declares 64 MB, 0x0C00_0000 – 0x0FFF_FFFF) | `RTL/CPU/CPU_PLIC` inside `CPU_TOP` | Peripheral, no |
| 0x1000_0000 – 0x1001_FFFF | 128 KB | **ROM**: the LiteX BIOS (48,564 bytes used); reset vector | LiteX `rom` (block RAM) | Peripheral, no |
| 0x1100_0000 – 0x1100_1FFF | 8 KB | **SRAM**: the BIOS's data and stack until DRAM is up | LiteX `sram` (block RAM) | Peripheral, no |
| 0x1200_0000 – 0x1200_FFFF | 64 KB | **CSRs** of the peripherals (section 4) | LiteX | Peripheral, no |
| 0x3000_0000 – 0x3000_1FFF | 8 KB | **Ethernet packet buffers**: RX 2 slots at 0x3000_0000, TX 2 slots at 0x3000_1000, 2 KB each | LiteX `ethmac` | Peripheral, no |
| 0x8000_0000 – 0x8FFF_FFFF | 256 MB | **DRAM** (DDR3, MT41K128M16 × 2) | LiteDRAM, through `CPU_L2` | Memory, yes |

Nothing answers elsewhere: an access there ends with a bus error from the SoC bus (after its timeout) or an access
fault, depending on the bus. The JTAG debug module has no address on this map: the debugger reaches it over JTAG,
and its System Bus Access reads and writes the map above from the outside (`RTL/CPU/CPU_DBG/CPU_DBG_SPEC.md`).

Inside the CLINT (relative to 0x0200_0000): `msip` +0x0000, `mtimecmp` +0x4000, `mtime` +0xBFF8. `mtime` counts at
500 kHz (50 MHz / `CLINT_TICK_DIV` = 100; `timebase-frequency` of the device tree). Inside the PLIC (relative to
0x0C00_0000): priority +0x00_0000, pending +0x00_1000, enables +0x00_2000 + 0x80 × context, threshold and claim
+0x20_0000 + 0x1000 × context; context 0 is machine mode, context 1 supervisor mode.

## 4. Peripheral CSRs (0x1200_0000)

From `build/csr.csv` (generated by `scripts/build_soc.sh`; 2 KB each):

| Address | Block | Linux (device tree) |
|---|---|---|
| 0x1200_0000 | `ctrl` (reset, scratch, bus errors) | `litex,soc-controller` |
| 0x1200_0800 | `ddrphy` | (the BIOS only) |
| 0x1200_1000 | `ethmac` | `litex,liteeth` (with 0x3000_0000) |
| 0x1200_1800 | `ethphy` (MDIO) | `litex,liteeth` |
| 0x1200_2000 | `identifier_mem` (the SoC's name string) | — |
| 0x1200_2800 | `leds` | — (the bare-metal examples use it) |
| 0x1200_3000 | `sdcard` | `litex,mmc` |
| 0x1200_3800 | `sdram` (LiteDRAM controller) | (the BIOS only) |
| 0x1200_4000 | `timer0` | `litex,timer` |
| 0x1200_4800 | `uart` | `litex,liteuart` (`console=liteuart0`) |

## 5. Interrupts

| Source | LiteX IRQ | PLIC source |
|---|---|---|
| UART | 0 | 1 |
| timer0 | 1 | 2 |
| Ethernet | 2 | 3 |
| SD card | 3 | 4 |

PLIC source 0 does not exist, so `core.py` shifts the LiteX lines up by one. The CLINT gives the hart its software
and timer interrupts; the PLIC its machine (11) and supervisor (9) external interrupts. Linux's timer is the
S-mode timer of Sstc (`stimecmp`), counting the same `mtime`.

## 6. What runs where during the boot

| Step | Code | Runs from | Mode |
|---|---|---|---|
| 1 | LiteX BIOS: initialises DDR3 (`sdram`, `ddrphy`), tests it, reads `boot.json` from the SD card and loads the two files into DRAM | ROM 0x1000_0000, data in SRAM 0x1100_0000 | M |
| 2 | OpenSBI (`fw_jump.bin`, with the device tree inside): loaded at **0x8000_0000**; keeps 2 MB (LiteX region `opensbi`) and puts the device tree at **0x8240_0000** (`FW_JUMP_FDT_ADDR` of `scripts/build_opensbi.sh`) | DRAM | M |
| 3 | Linux (`Image`): loaded at **0x8020_0000** (`boot.json`), started by OpenSBI in S mode with the address of the device tree | DRAM | S |
| 4 | BusyBox or Debian from the SD card's second partition (`root=/dev/mmcblk0p2`) | DRAM (virtual memory, Sv39) | U |

`software/boot/boot.json`:

```json
{
    "Image":       "0x80200000",
    "fw_jump.bin": "0x80000000"
}
```

The bare-metal programs of `software/baremetal/` (`docs/ECLIPSE.md`) take the place of steps 2 to 4: they are
linked at 0x8000_0000 and loaded over JTAG once the BIOS has set the DRAM up.

## 7. Where the numbers are defined

| What | File |
|---|---|
| Base addresses (CLINT, PLIC, ROM, SRAM, CSR, Ethernet buffers, DRAM), `MEM_BASE`, the reset vector | `LitexSystem/cpu/mmrisc/core.py` (`mem_map`, `set_reset_address`) |
| The CSR addresses and the IRQ numbers LiteX assigned | `LitexSystem/build/csr.csv`, `csr.json` (generated) |
| What Linux is told | `LitexSystem/software/mmrisc_arty.dts` (built into `fw_jump.bin`) |
| Where the BIOS loads OpenSBI and Linux | `LitexSystem/software/boot/boot.json` |
| Where OpenSBI puts the device tree | `LitexSystem/scripts/build_opensbi.sh` (`FW_JUMP_FDT_ADDR`) |
| Defaults of the RTL (`RESET_VECTOR`, `MEM_BASE`, `CLINT_BASE`, `PLIC_BASE`) | `RTL/CPU/CPU_TOP/CPU_TOP.sv` |

The map is the one of the Rocket configuration of LiteX, byte for byte, which is what let the first Linux
boot reuse its device tree (`docs/BRINGUP.md`). If one of these changes, the device tree has to change with it.

## 9. The ROM in logic simulation (`SIM/SIM_BIOS`)

The simulation of the BIOS and of the Linux boot runs the same `CPU_TOP` as the board, with the reset vector at
0x1000_0000 like the board (`RESET_ADDR` of `tb_BIOS.sv`), so the first fetches go uncached over the peripheral
bus as on the board. What answers there is a model in the testbench, not the block RAM of LiteX:

| Region | Model |
|---|---|
| ROM 0x1000_0000, 128 KiB | `logic [63:0] rom[0:16383]` in `SIM/SIM_BIOS/LITEX_PERIPH.sv`. A read returns `rom[(addr − 0x1000_0000) >> 3]` (the address aligned to 8 bytes, the 64-bit peripheral bus of `CPU_TOP`); a write is ignored |
| SRAM 0x1100_0000, 8 KiB | An array in the same file |
| CSRs 0x1200_0000 | `ctrl`, `timer0` and the UART in `LITEX_PERIPH.sv` (the UART after `litex/soc/cores/uart.py`, a TX FIFO of 16, its interrupt on PLIC source 1 as in the SoC); the `sdcard` CSRs are passed on to `SD_MODEL.sv`; the other CSRs read as zero |
| DRAM 0x8000_0000, 256 MiB | `AXI4_SLAVE_MEM` (`SIM/SIM_CPU`), an AXI4 memory that answers at once unless a latency is given (`+rlat=` / `+blat=`, the DDR3 of the board) |

What the ROM holds depends on the mode of the run:

| Mode | ROM | DRAM at the start |
|---|---|---|
| **BIOS mode** (`make run`, `make check`) | **The real LiteX BIOS**: `LitexSystem/build/software/bios/bios.bin`, the same file as in the bitstream, made into `bios.hex` and read with `$readmemh` | Empty |
| **Linux mode** (`+linux`: `make linux`, `linux-initrd`, `linux-sd`, `linux-tlb`, `linux-perf`) | **A stub of three double words** written by the testbench instead of the BIOS (below) | `fw_jump.bin` at 0x8000_0000 and `Image` at 0x8020_0000, as the BIOS would have left them after loading `boot.json`; with `linux-initrd`, also the initramfs at 0x8200_0000 |

The stub of Linux mode sets `a0` to hart 0 and jumps to OpenSBI:

```
addi t0,x0,1 ; slli t0,t0,31     # t0 = 0x8000_0000
addi a0,x0,0 ; addi a1,x0,0      # a0 = hart 0, a1 = 0
jalr x0,0(t0) ; nop              # to OpenSBI
```

Why the Linux runs do not go through the BIOS:

- **The DDR3 training is not modelled.** The BIOS trains the DDR3 through `ddrphy`, and the memory model has nothing
  to train; even in BIOS mode the training after "Initializing SDRAM" fails. So BIOS mode passes when the BIOS has
  got that far (the banner and the whole SoC report printed) and has taken at least one UART interrupt, which is
  what the board lacked at the first bring-up (`docs/BRINGUP.md`).
- **Time.** Loading about 16 MB from the SD card model through the BIOS would take far longer than the boot itself.

So the work is split: BIOS mode checks the BIOS itself (the uncached fetch from the ROM and its interrupts), Linux
mode checks the boot from OpenSBI on, and the root file system comes from the SD card model (`SD_MODEL.sv`,
`linux-sd` and the runs after it) or from an initramfs in memory (`linux-initrd`).
