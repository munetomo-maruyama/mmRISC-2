# 性能測定(2026-10)

CoreMark と Dhrystone を、(1) シミュレーション(`SIM/SIM_SYS`、マシンモード、
コア + 実キャッシュ)と (2) 実機(Arty、50 MHz、Linux のユーザプログラム)で測る。
シミュレーションでは計時部分のサイクル数と命令数が正確に分かり、どこでサイクルを
失っているかを数えられる。実機の数字はメモリ(DDR3)と OS を含んだ実力。

| 環境 | 作り方 | 走らせ方 |
|---|---|---|
| シミュレーション | `SIM/SIM_SYS/bench/`(C ライブラリなし、CoreMark の `ee_printf`) | `cd SIM/SIM_SYS && make bench` |
| 実機 | `LitexSystem/software/bench/`(静的リンク、glibc) | `software/bench/README.md` |

コンパイラはどちらも GCC 13.2、`-march=rv64imafdc -mabi=lp64d -O2`。

## 1. シミュレーション(計時部分のみ)

| | CoreMark(10 回) | Dhrystone(500 回) |
|---|---|---|
| サイクル | 5,834,958 | 426,006 |
| 命令 | 3,589,223 | 202,550 |
| CPI | 1.626 | 2.103 |
| 1 回あたり | 583,496 サイクル | 852 サイクル(405 命令) |
| **性能** | **1.71 CoreMark/MHz** | **0.67 DMIPS/MHz** |

(Dhrystone の文字列関数は自前の 1 バイトずつの版で、実機の glibc より遅い。
CoreMark は計時部分にライブラリを呼ばない。tb_SYS のメモリは DDR3 より速く答える。)

### どこでサイクルを失っているか(発行点 ID → EX で数えたもの)

`+profile` の「where an instruction is issued」。各サイクルは、命令を EX へ発行したか、
発行できなかった理由のどれか 1 つに数えられ、合計が総サイクルになる。

| | CoreMark | Dhrystone |
|---|---|---|
| 発行した | 61.5 % | 47.5 % |
| **EX 停止: MA が D$ の応答待ち** | **23.6 %** | **33.8 %** |
| 分岐予測ミス(リダイレクト + 詰め直し) | 6.6 % | 11.2 % |
| EX 停止: MDU / FPU | 4.8 % | 4.3 % |
| EX 停止: ロードユース | 3.5 % | 3.2 % |
| その他(フェッチ、直列化、変換) | 0.0 % | 0.0 % |

| 予測ミス / 実行 | CoreMark | Dhrystone |
|---|---|---|
| 条件分岐 | 82,387 / 582,985(14 %) | 3,506 / 28,002(13 %) |
| `jal` | 7,996 / 43,640(18 %) | 6,008 / 8,503(**71 %**) |
| `jalr`(主に関数の戻り) | 7,055 / 21,377(33 %) | 4,008 / 7,003(57 %) |
| 1 回の予測ミスの損失 | 約 3.9 サイクル | 約 3.5 サイクル |

### 読み取れること

1. **D$ のヒットでも、ロード / ストア 1 回ごとに約 1 サイクル止まる**(最大の損失、
   23〜34 %)。D$ は毎サイクル 1 アクセスを受けられる(`CPU_CACHE_SPEC.md` 8 章)が、
   要求から応答までは 2 サイクルかかる。コアは MR で要求を出し、命令が MA にいる
   次のサイクルに応答を待つので、MA が 1 サイクル待ち、後ろの命令もすべて止まる。
   データアクセス 1 回あたりの停止は 1.08〜1.12 サイクルで、ほぼ全部がこれ。
2. **`jal` と `jalr` の予測ミスが多い**。`jal` の飛び先は命令そのものに書いてあるのに、
   BTB(64 エントリ、直接写像)に無いと EX まで分からない。関数の戻り(`jalr`)は
   呼び出し元ごとに飛び先が変わるが、戻りアドレススタックが無い。
3. MDU(乗算 3 サイクル、除算 32/64 サイクル)が 4〜5 %。

### 1 つだけシミュレーションと合わなかった数字 → 分岐予測の置き場所の制約

`micro` の整列ロードのループ(4 命令、全部 D$ ヒット)が実機で 10.5 サイクル / 回、
シミュレーションでは 6.3 だった。同じ命令列を両方で走らせて切り分けた(`loops.h`、
`micro 50 loops` / `sweep`、`SIM/SIM_SYS/bench/ldloop.c`):

| ループ | 分岐の番地 | 8 バイト語内の位置 | 実機 | シミュレーション |
|---|---|---|---|---|
| ロードなし | — | — | 4.56 | 4.29 |
| `ld` 同じ語 | 0x10d8e(2 バイトの `c.bnez`) | 6 | 6.59 | 6.32 |
| `ld` ストライド 8 | 0x10d4c | 4 | 6.62 | 6.42 |
| `ld` ストライド 64(`loops`) | 0x10d9e | **6(後半が次の語)** | **10.81** | 6.31 |
| `ld` ストライド 64(`sweep`、64 ライン) | 0x1097a | 2 | 6.58 | 6.19 |

キャッシュでもページングでもなく(4 KiB ページの 3 段のページテーブルでもシミュレーションは
6.30)、ループの **32 bit の分岐が 8 バイトのフェッチ語の最後の 2 バイトから始まり、後半が
次の語に掛かっている**ことが原因だった。BTB はこの位置の分岐を予測しない
(`CPU_CORE_SPEC.md` 決定 33・34)ので、毎回予測ミスになり、約 4.5 サイクル失う。
シミュレーションのループは、たまたま分岐が語の中に収まる位置にあった。

C 拡張のコードでは 32 bit 命令の開始位置が 2 バイト単位でばらつくので、この位置に来る
分岐は珍しくない。プロファイルで数えると:

| | CoreMark | Dhrystone |
|---|---|---|
| 語をまたぐ 32 bit の分岐 / `jal`(実行数) | 171,935 / 626,625(27 %) | 6,001 / 36,505 |
| そのうち予測ミス | 52,164 = **予測ミス全体の 54 %** | 4,501 = 33 % |
| 損失(× 約 3.9 サイクル) | 総サイクルの約 3.5 % | 約 4 % |

## 3. 改善の候補(効果の大きい順)

| 候補 | 見込み | 規模 | 内容 |
|---|---|---|---|
| A. D$ ヒットで MA を止めない | CoreMark 最大 +31 %、Dhrystone 最大 +51 % | 大 | 応答を 1 サイクル早める(BRAM の出力からウェイ選択まで 1 サイクルに入れる。タイミングが厳しい)か、ロードの結果を MA の 1 サイクル後に書く形にする(ロードユースの間隔が延び、バスエラーの精密例外の扱いを決め直す必要がある) |
| B. 語をまたぐ 32 bit の分岐も予測する | CoreMark 約 +3.5 %、Dhrystone 約 +4 % | 中 | 決定 34 の制約を外す。予測を、分岐の後半が入っている次の語で使う(または前半の語のエントリが次の語のフェッチを待ってから飛ぶ) |
| C. `jal` を ID で飛ばす + 戻りアドレススタック | CoreMark 約 +1 %、Dhrystone 約 +9 % | 中 | `jal` は飛び先が即値なので ID でリダイレクトでき、BTB 外れでも 1〜2 サイクルで済む。`jalr` の戻りは小さなスタックで当てる。B と重なる分がある(語をまたぐ `jal`) |
| D. 乗算器の短縮 | 数 % | 小〜中 | 3 サイクル → 2 サイクル(DSP のパイプライン) |
| E. 不整列アクセスのハードウェア対応(課題 6) | 普通のコードでは 0 | 大 | 1 回 1629 サイクルを数サイクルにする。不整列アクセスを多用するコード(パケット処理など)でだけ効く |

見込みは、その分の停止がそのまま消えると仮定した上限(A は D$ 待ちの全部、B は語をまたぐ
分岐の予測ミスの全部、C は `jal` / `jalr` の予測ミスの全部)。

## 7. 乗算の短縮(2026-10-03、シミュレーション)

`CPU_CORE_SPEC.md` 決定 61。MUL / MULW の EX の待ちを 3 → 1 サイクル、MULH 系を 3 → 2 に。

| | 前 | 後 | |
|---|---|---|---|
| CoreMark(10 回) | 4,312,829 サイクル | **4,124,913** | **+4.6 %、2.42 CoreMark/MHz**(CPI 1.149) |
| CoreMark の EX 停止: MDU | 281,880(6.5 %) | 93,960(2.3 %) | 乗算 93,960 回 × 1 |
| Dhrystone(500 回) | 253,069 | 252,069 | +0.4 % |

Dhrystone の MDU 待ち(17,195 サイクル、6.8 %)は約 500 回の**除算**(1 回 34 サイクル前後)で、
乗算の短縮は効かない。除算の早期終了(被除数の先頭の 0 を飛ばす、Rocket の
`divEarlyOut` 相当)で縮められる。

実機(2026-10-03、配置配線後 WNS +0.162 ns): **2.313 CoreMark/MHz**(2.213 から +4.5 %)、
1.302 DMIPS/MHz(+0.3 %)。シミュレーションの比のとおり。

## 9. gshare(2026-10-03、シミュレーション)

`CPU_CORE_SPEC.md` 4.2・決定 63。条件分岐の向きを、ワードのアドレスと大域履歴で引く
2bit カウンタの表(8192 エントリ、履歴 12 ビット)から取る。

| | 前 | 後 | |
|---|---|---|---|
| CoreMark の条件分岐の予測ミス | 54,001 / 582,985(9.3 %) | **31,435(5.4 %)** | −42 % |
| CoreMark(10 回) | 4,124,913 サイクル | **4,033,497** | **+2.3 %、2.48 CoreMark/MHz**(CPI 1.124) |
| Dhrystone(500 回) | 237,406 | 233,430 | +1.7 % |

表の大きさと履歴の取り方を掃引した(CoreMark の条件分岐の予測ミス):

| 方式 | 1024 | 4096 | 8192 | 16384 |
|---|---|---|---|---|
| 成立した転送の行き先 2 ビット(経路履歴)、履歴を下位に折り込み | 61,684〜76,718 | | | |
| 同、上位に折り込み・初期値 weakly taken | 56,548 | 50,556 | | |
| **条件分岐の向き 1 ビット**(採用) | 48,592 | 36,150 | **31,435** | 31,801 |

経路履歴はループの戻りの分岐が履歴を埋め、以前の BTB のカウンタ(54,001)とほとんど
変わらなかった。履歴を下位ビットに折り込むと、近くのワードの分岐どうしが衝突して
かえって悪くなった。

`t24_predict` に 6(1 回おきに成立する分岐。履歴が無いと半分外れる)と 7(行き先の
変わる jalr。それまで BTB の行き先の更新を落とす変異 M175 を見つける試験が無かった)を
足し、4 の分岐を 1 回おきから定数のビット列に変えた(gshare が 1 回おきを当てるように
なり、戻りアドレススタックの復元を試す予測ミスが起きなくなったため)。

なお `SIM_SYS` の CoreMark が出す `Errors detected` は、実行時間が 10 秒未満だと
CoreMark 自身が数えるもので、CRC の検査は通っている(実機の `bench.sh` は 10 秒以上
走らせるので出ない)。

実機(2026-10-03、配置配線後 WNS +0.094 ns、LUT 42,323 = 66.8 %): **2.358 CoreMark/MHz**
