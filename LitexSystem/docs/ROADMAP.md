# 次の設計テーマ(2026-10-05 時点)

A・B のテーマ(2026-10-03 に整理したもの)をすべて終えた時点での整理。実機(Arty A7-100T、
50 MHz、Linux 7.2)で **2.747 CoreMark/MHz(Zba/Zbb で作ったもの、rv64gc なら 2.462)、
1.482 DMIPS/MHz**、WNS +0.452 ns、**LUT 45,598 / 63,400(71.9 %)、ブロック RAM 40.5 / 135
タイル(30 %)**。PMU(B5)で、実機の Linux 上で内訳を数えられるようになった。

## 1. いまの姿(実機の PMU で数えた CoreMark、`BENCH.md` 13 章)

CPI 1.134。1000 命令あたり 134 サイクルの損失の内訳:

| 要因 | サイクルに対して | 見通し |
|---|---|---|
| フロントエンドが空(予測ミスの詰め直し、I$ ミス) | 4.8 % | 条件分岐の 7.2 % が外れ、1 回約 5 サイクル。予測器を大きくしても 1〜2 % |
| MDU / FPU 待ち(主に乗算の 1 サイクル) | 2.6 % | ほぼ下限 |
| ロードユース | 2.0 % | 1 サイクルでヒットする D$ が要り、50 MHz では現実的でない |
| 予測ミスのリダイレクト | 約 1.4 % | フロントエンドの行と同じく、予測ミスが減れば減る |
| D$ 待ち | 0.7 % | CoreMark はデータが小さい |

CoreMark のようにキャッシュに収まる負荷では、パイプラインの残りはどれも数 % 以下。
一方 `micro` では、8 MiB を追いかけるロードが 1 回 75 サイクル、8 MiB の読み出しが 54 MB/s。
キャッシュに収まらない負荷(Linux の実際の仕事)はメモリ階層で決まっているはずだが、まだ
測っていない。**次は CoreMark の外を測るところから始める**のがよい。

## 4. 勧める順序

1. **H1 + G1 + H2**(実機の時間と文書だけ。B4 / B5 の締めくくり)
2. **D1**(+ 必要なら D2): CoreMark の外を測る
3. **D1 でメモリ待ちが大きければ E1(L2)**。TLB が目立てば E3
   (2026-10-06、D1 の結果: どちらも効く。E1 はカーネルの負荷で 20〜30 %、E3 はユーザモードで
   5〜15 %。`BENCH.md` 14 章)
4. 合間に **F1(Zbs)**、Linux への効きが見えれば F2 / F3、G2
5. C1 / C2 は負荷が見えてから(前回と同じ)、C3(ASIC)はコアが落ち着いた時点で
