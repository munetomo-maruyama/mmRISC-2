1. はじめに

1.1 目的

  • 64-bit RISC-V CPU(RV64GC)を自作し、FPGA ボード Arty A7-100T で Linux を動かす。
  • 自作するのは CPU コアのハードウェアだけとする。周辺回路と SoC は LiteX、ソフトウェアは OpenSBI・Linux・BusyBox を既存のまま使う。
  • 設計は Claude Code に任せる。仕様書・RTL・テストベンチ・スクリプト・文書を書くのは Claude Code で、筆者は目標を決め、提案から選び、Vivado と実機を受け持つ。
問い: AI はどこまで CPU を設計できるか。人は何をすればよいか。

「CPU だけを作り、ほかは既存のものを流用する」という制約を最初に置いたことが、短期間で Linux まで到達できた大きな理由の一つである。

3.2 Linux システム

LiteX が生成する SoC の CPU を mmRISC-2 に差し替えた。最初は Rocket 構成とメモリマップを 1 バイト単位で合わせ、デバイスツリーは CPU のノードだけを書き換えた。その後、LiteX の L2 を外して CPU 内の L2 を使い、DMA を D$ 経由にし、Ethernet を足した。ソフトウェアは LiteX BIOS → OpenSBI v1.9 → Linux 7.2 → BusyBox の順に起動する。

4. 開発の経緯

4.1 最初に手をつけたこと(09-15〜09-20)

CPU 本体の前に、バスとメモリ、デバッガの経路を確かめた。CPU が動かないときに、どこまでが正しいかを切り分けられるからである。デバッガは、公式の Debug Spec の PDF を渡して CPU より先に実装させ、09-17 に FPGA 上で OpenOCD からメモリの読み書きと cJTAG の再接続を確かめた。このデバッガは、後に実機の Linux カーネルにハードウェアブレークポイントを置くのにも使った。その後は「テストベンチから先に作る」を基本とし、キャッシュは参照モデルとランダムの試験を作ってから RTL を書いた。

4.2 日程の実績

09-20〜21 の 2 日で CPU コア(パイプラインの骨格から LiteX への組み込みまで)を作り、09-22〜24 の 3 日をタイミングに使った。09-24 に実機で BIOS、09-25 に Linux が起動した。10 月に入ってからは性能と計測、10-10〜12 はメモリ待ちとタイミングの残りに取り組んだ。

4.4 性能の推移

初版(10-01)の 1.584 CoreMark/MHz から、D$ のヒットを 2 サイクルに、ロード・ストアを EX から早出し、乗算を 1 サイクルに、gshare、ロードの値による分岐を MR で解決、Zba / Zbb、L2、最後にコンパイラのオプション、と積み上げて、CoreMark は +91 %、Dhrystone は +87 % になった。

CoreMark はキャッシュに収まるため、Linux の実際の負荷を 8 つ選び、PMU で数えた(workload.sh)。カーネルが主の負荷ではキャッシュ待ちがサイクルの 50〜70 % を占めていたので、L2 を入れて 1.2〜1.7 倍にした。その後、ストアのミスを待たない、汚れた追い出しより先に読み込む、cbo.zero、バスの改善で、さらに 7〜11 % 下げた。関数ごとの内訳(perf)を見て、Zbc による CRC の高速化も確かめた。

4.5 FPGA のタイミング(WNS)の推移

最初の合成は −20.4 ns(約 25 MHz 相当)だった。原因を配線の混雑ではなく論理の段数と見て、経路を読んで切っていった。途中の段階 2 は逆に悪化してやり直し、最後はステージ MR を足して 09-24 に 50 MHz を満たした。その後も機能を足すたびに WNS は 0 付近に戻り、そのたびに最悪経路を読んで直した(T1〜T7)。Rev.01 では +0.664 ns である。

5. 手戻りと検証

AI が間違えた例と、それを何が捕まえたかを 3 つ挙げる。

5.1 手戻り①: 起動時のバナーが「__」で止まった(09-24)

␣␣␣␣␣␣␣␣__▌ ␣ = 空白、▌ = ここで止まる

最初の実機で、LiteX BIOS のバナーの途中で止まった。送れたのは UART の送信 FIFO の 16 バイト(改行 \n\r の 2 + 太字の制御コード ESC[1m の 4 + 見える 10 文字)である。CPU は動いていて、止まっていたのは割り込みだった。

  • 原因: キャッシュ無しのアクセスでアドレスを 8 バイトに丸めていた。PLIC の +4 番地への書き込みが「下半分・ストローブ無し」になって消え、割り込みが来ない。UART の送信は 16 バイトの FIFO を超えると割り込み待ちになる。
  • なぜ見逃したか: シミュレーションのメモリモデルはバイト単位でアドレスを受け、SoC のテストは外部割り込みを 0 に固めていた。本物の BIOS を割り込み込みで走らせたことがなかった。
  • 何で捕まえたか: 本物の bios.bin と UART のモデルを載せた SIM_BIOS を作り、直す前の RTL が同じところで止まることを再現してから直した。SIM_BIOS はその後、Linux の起動まで回す回帰試験になった。

翌日には、satp を書いた後に命令を取り直さない不具合(MMU を S モードで有効にする手順)も見つかった。どちらも「実機で初めて通る道」だった。

5.2 手戻り②: 実機では遅くなったプリフェッチ(10-11)

  • I$ の次ラインのプリフェッチを入れると、Linux の起動のシミュレーションで CPI が −1.1 %、プリフェッチの 48 % がミスを救った。
  • しかし実機では 0〜4 % 遅くなった。使われないプリフェッチのバーストの後ろで、本当のミスが待っていた。
  • 原因: シミュレーションのメモリは即答し、実機の DDR3 は数十サイクルかかる。
  • 対策: シミュレーションにメモリの遅れのモデル(読み 20、書き 10 サイクル)を入れると、シミュレーションでも +1.2 % と実機と同じ判定になった。

プリフェッチは切り、以後は作る前に測るようにした。例えば、バスに 2 本目の読み出しを受けさせる改造は、効果が 0.26 % しかないと先に分かったので作らなかった。AI はシミュレーションの前提(メモリが即答)を疑わずに「速くなった」と報告した。実機の数字が、前提の誤りを教えた。

5.3 手戻り③: AI の報告の誤りと、環境の罠

報告の誤り(10-12)

  • Zicboz を入れたとき、キャッシュのバグ注入を「59 / 59 検出」と報告してコミットした。
  • 実際は 56 / 59。名前の変更で 3 つの変異が当たらなくなっていた。
  • ログの最後の 3 行だけを見て要約していた。次の変更の検証で自分で気づき、訂正した。
  • → 規則をメモに残した: 「NOT DETECTED / NOT APPLIED を全行出して、数を突き合わせる」。

環境の罠(09-21、10-05)

  • SD カードに書いたファイルが、差し直すと消えていた。原因は macOS が、VM に渡す前にマウントしていた古い FAT を、カードが戻ったときに書き戻していたこと。Claude Code が FAT のタイムスタンプから順番を割り出した。→ 「第 1 パーティションは Mac から書く」を手順とメモに。
  • 共有フォルダはファイルの時刻が 1 秒単位のため、直した RTL を make が「変更なし」と見なし、古いシミュレータで試験していた。→ ソースのハッシュで判定する形に直した。

AI の誤りは「もっともらしい要約」に出る。生のログを見る規則で防げる。環境の罠は人の手元にあり、AI は記録から原因を推理できる。

7. まとめと今後

7.1 まとめ

  • Claude Code で RV64GC の CPU を設計し、12 日で Arty A7-100T の Linux を起動した。
  • 30 日で Rev.01: L2、FPU パイプライン、Zbc / Zicboz、CoreMark 3.0 /MHz、WNS +0.664 ns、120 分の負荷試験 PASS。
  • 人の役割は、目標と判断、実機、そして AI の報告を確かめることである。

7.2 次のテーマ(ROADMAP)

Rev.01 のタグは main に置き、開発は dev ブランチで続ける。実機の負荷を関数ごとに測った結果から、次の順で進める。

  • 2 段目の TLB: ユーザモードの負荷では、ページテーブルの探索がサイクルの 10〜13 % を占める。
  • ライン全体を書くときは読まない(write-validate): カーネルのユーザ空間へのコピーで、コピー先のラインの読み込みを省く。
  • キャッシュ無しのストアを待たない(posted store): ドライバの書き込み(例: Ethernet の送信)。

7.3 次の構想: mmRISC-3(仮称)

同じ Arty A7-100T で、RV64GC の dual-issue / out-of-order コアに Linux を載せられるかを机上で検討している(まだ設計はしない)。

見通し

  • 資源の再配分の設計になる: スライスはすでに 86 %。L2 を縮め、LUT から BRAM・LUTRAM・DSP へ移す。
  • 目安: FPGA 向け OoO の NaxRiscv RV64 は、コアで約 18k LUT(FPU・Zb 系なし)。
  • 50 MHz に据え置き、段数を減らして資源を節約する。
  • 最大の分かれ目は FPU の扱い(専用リネーム / 整数と統合 / 縮小)。

mmRISC-2 から分かっていること

  • ミスしたロードの値は 1〜2 命令後に使われる → 複数のミスを同時に出せる D$・L2 が前提(いまのバスは読み出しを 1 本ずつ)。
  • Linux の急所は副作用を投機させないこと: MMIO のロード、CSR、AMO、例外、デバッグ、トリガはコミット時に。
  • 期待: CoreMark は約 1.6 倍が天井、カーネルの負荷は 1.2〜1.4 倍。

進め方は、資源の内訳を測る → NaxRiscv RV64 を Arty で実測 → 1-wide OoO で Linux を起動 → 2-wide に → 投機ロードとミスの多重化 → FPU と予測器、の順とする。検証は、これまでの参照モデル・バグ注入・SIM_BIOS を引き継ぎ、コミット時に Spike と突き合わせる仕組みを最初から入れる。収まらなければ、デュアルイシューの in-order か、1-wide OoO で止める。
